# 先行者が示した、理解支援の要は「なぜ」と「隠さない」

**結論**: PR・大きな差分・複雑なコードを理解しやすくする仕組みには、40 年分の先行者がいる。並べ方（ファイル順・流れ順）の効果を最も丁寧に確かめたのは Tobias Baum で、理論から「関連する変更をまとめ、まとめ方を見せよ」という 6 原則を導いた。ところが本人の 50 人実験では、**順序が効率を上げるとは確かめられなかった**。確かに測られているのは次の 3 点である。**レビューで最も難しいのは「変更の理由」の理解**であること（Bacchelli & Bird 2013、Ko 2007）。**後ろに置いたものは見落とされる**こと（Fregnan 2022 では、最後に置いたファイルの欠陥は発見のオッズが 64% 低い）。**作業記憶は離れた場所にまたがる欠陥の発見にだけ効く**こと（Baum）。LLM 時代の測定はどれも同じ向きを指している。生成された説明やレビューは処理量・マージ率・解決率を上げるが、人の理解や網羅性には中立か、むしろ悪い（生成レビューを出発点にすると指摘箇所に集中して他を探さなくなる、AI 利用群は理解テストが 17 ポイント低い）。失敗例は、作るコストが高すぎた（Distill、literate programming）、一般化しすぎた（Subtext）、自動の絞り込みが必要なコードまで隠した（Flowistry、CodeTour 研究）、ノイズで信頼を失った（FindBugs、AI レビューの nit）の 4 型にまとまる。ここから pr-tour や pr-review に移せる原理は次のとおり。冒頭に「なぜ」と前後の違いを置く。全変更を網羅して隠さない。推論と検証済みを分ける。熟練した読者には説明を減らす。人が先に考えてから AI の説明を見せる。効果は「わかりやすかった」でなく理解の結果で測る。一方で、**PR ツアーが理解や欠陥発見を改善したという対照実験は、まだ一つも見つかっていない**。

この報告は 5 本の調査ノート（業界ツール、プログラム理解研究、認知負荷理論、explorable explanations と tools for thought、LLM 時代と日本語圏の実務者）を統合したものである。数値の多くは論文本文で確かめたものだが、要旨や検索要約にしか当たれていないものもあり、その場合は「（要旨のみ）」「（検索要約のみ）」と書いた。2026-11-21 にこれらを一次資料の本文で確かめ直し、確認できたものは「本文で確認」に改め、食い違ったものは訂正した。照合の記録は [verification.md](../research_notes/課題とバグの理解支援%20先行事例/verification.md) にある。「推論」と書いた箇所は Claude の推論で、ユーザーの判断ではない。

## 先行者は 4 つの系譜に分かれ、2026 年に「PR ツアー」で合流した

人を起点に整理すると、先行者は 4 つの系譜に分かれる。1 つ目は **「変更を理解できる単位に分け、順に読ませる」レビューツールの作り手** である。Phabricator の Evan Priestley、Meta の stacked diffs から Graphite へ移った Tomas Reimers と Greg Foster、「前回読んだ版からの差分」を発明した Jane Street Iron の Yaron Minsky、Review Board の Christian Hammond、Reviewable がここに入る。2 つ目は **プログラム理解・コードレビュー研究者** で、チューリッヒ大学の Alberto Bacchelli を軸にした共著網（Baum、Fregnan、Wurzel Gonçalves、Spadini、di Biase）と、Microsoft Research の系統（Bird、DeLine、Venolia、Ko、LaToza、Barnett）が中心である。3 つ目は **認知負荷理論と教授設計** の Sweller、Kalyuga、Mayer、Pollock と、それをプログラミングに移した Margulieux、Guzdial、Sorva、Fakhoury である。4 つ目は **見えないものを見せ、問いごとに道具を作る** 人々で、Bret Victor、Tudor Gîrba（feenk）、Geoffrey Litt（Ink & Switch）、Andy Matuschak と Michael Nielsen、Philip Guo（Python Tutor）、Jonathan Edwards（Subtext）がいる。

2025〜2026 年には、3 つ目と 4 つ目の系譜を実装した「AI 生成の PR ウォークスルー」が 5 社以上からほぼ同時に出た。CodeRabbit Change Stack（2026-05）、Cursor/Graphite の Code Tours、Sourcegraph guided diff tour（2026-08）、balade、そして YunSinLee の pr-tour（リポジトリ作成 2026-09-12）である（[CodeRabbit](https://www.coderabbit.ai/blog/introducing-change-stack-the-first-ai-native-code-review-interface)、[Cursor docs](https://cursor.com/docs/origin/code-tours)、[Sourcegraph changelog](https://sourcegraph.com/changelog/guided-diff-tour-beta)、[balade](https://github.com/basaltbytes/balade)、[pr-tour](https://github.com/YunSinLee/pr-tour)）。並べ方はどの製品でも依存順か流れ順に収束しており、差別化の軸は「誰が説明を書き、その信頼をどう担保するか」に移っている（推論）。pr-review が目指す「チームの共有メンタルモデル」には、別系統の先行者がいる。Google の Critique 研究は、レビュー導入の主目的が欠陥発見ではなく教育だったと報告した（「code must act as a teacher for future developers」、[Sadowski ほか ICSE-SEIP 2018](https://sback.it/publications/icse2018seip.pdf)）。Storey は 2026 年、AI で速く進むチームが共有理論を失う現象を「cognitive debt」と名付けた（[Storey](https://margaretstorey.com/blog/2026/02/09/cognitive-debt/)）。

## 測られた事実は「なぜ」の欠如と注意の偏りを示し、順序の効果は示していない

最も強く、何度も独立に再現されている事実は、**理解の最大の障害が「なぜ変えたか」だ**ということである。Bacchelli と Bird は Microsoft の 17 人を観察し、873 人の開発者を調査した。そのうえで「the most difficult thing when doing a code review is understanding the reason of the change」という面接の言葉を報告し、慣れないファイルのレビューに時間がかかると答えた人が 91% いたことも示した（[ICSE 2013](https://sback.it/publications/icse2013.pdf)）。Ko らの 2007 年の観察でも、最も満たされにくい情報ニーズは設計についての問いだった（[Ko, DeLine, Venolia](https://faculty.washington.edu/ajko/papers/Ko2007InformationNeeds.pdf)）。Baum の調査ではレビュアーが最初に要求と全体像を知りたがった（[Baum 2017](https://tobiasbaum.github.io/rp/optimalordering.pdf)）。Söderberg らはレビューの最初に「オリエンテーション段階」があると見いだした（[CRDM](https://arxiv.org/abs/2507.09637)）。2007、2013、2017、2025 年と、別々の研究が同じ結論に達している。日本の 2026 年の調査（キッカケクリエイションによる、コードレビューを担当する IT エンジニア 322 人へのインターネット調査）では、AI 生成コードのレビューで問題だと感じた点（3 つまで選択）として、**49.5% が「提出者本人がコードの内容を説明できなかった」** を挙げ、これが最多だった（[@IT](https://atmarkit.itmedia.co.jp/ait/spv/2606/16/news041.html)。Shift_JIS として読み直して本文で確認し、「経験を挙げた」から訂正）。AI が書いたコードでは、作者に聞いても「なぜ」が手に入らないことがある。

次に強いのは **表示順が注意を配分する** という事実である。Baum のログでは、53% のセッションでレビュアーはツールが最初に示したファイルから読み始めた（[Baum 2017](https://tobiasbaum.github.io/rp/optimalordering.pdf)）。Fregnan らは 219,476 PR を分析し、先に表示されたファイルほどコメントが多いことを示した。106 人の実験では、ある種類の欠陥を最後に置くと発見のオッズが 64% 下がった（[arXiv 2208.04259](https://arxiv.org/abs/2208.04259)）。2026 年には、1,355 人の開発者のうちアルファベット順を最適と考える人は 10.2% にとどまり、66% が依存関係を考慮したまとめ方や並べ替えの設定を求めた（[Rahman, Codabux, Roy, ICSE 2026](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/310/Breaking-the-Alphabet-Rethinking-File-Ordering-in-Code-Review)、要旨のみ。要旨は「dependency-aware grouping and customizable file ordering (requested by 66% of reviewers)」と 2 つをまとめて書いており、「依存関係でまとめた順序を望んだ」から訂正。本文は取得できず）。

ところが、**関連の順に並べれば効率が上がるかは確かめられていない**。Baum は自分の理論を、主に専門開発者の 50 人で検証した。結論は「We cannot conclude reliably whether the order of presenting the code change parts influences the efficiency of code review.」だった（[Baum EMSE](https://tobiasbaum.github.io/rp/memoryCodeOrderAndReview.pdf)）。同じ実験で作業記憶容量が効いたのは、離れた場所にまたがる欠陥（delocalized defects）の発見だけだった。di Biase らは、混ざった変更を 2 つの PR に分けて見せた。欠陥の発見数（20 対 17）、理由の理解、所要時間には差が出ず、有意に減ったのは誤指摘（6 対 1、p=0.03）だけだった（[PeerJ CS 2019](https://pmc.ncbi.nlm.nih.gov/articles/PMC7924728/)）。ここから推論できるのは、順序や分割で救えるのは「見落としの偏り」と「誤指摘」であり、「理解の速さ」ではないかもしれないということである。

認知負荷理論は、この結果に理論上の説明を与える。内在的負荷（課題そのものから来る負荷）は消せない。できるのは、要素をいったん切り離して見せてから全体を相互作用させること（Pollock らの 2 段階法、[UOW](https://ro.uow.edu.au/edupapers/145)、要旨のみ）と、部品の名前と性質を先に教えること（Mayer の pretraining、[Cambridge Handbook](https://www.cambridge.org/core/books/cambridge-handbook-of-multimedia-learning/principles-for-managing-essential-processing-in-multimedia-learning-segmenting-pretraining-and-modality-principles/4110A2275F6DCD02DAB1F8B37BA7E5CE)）で、時間方向に分散させることだけである。さらに **熟達化反転効果** がある。初心者に効く詳しい誘導は、熟練者には既有の知識と照合する余計な負荷になり、成績を下げる。PLC のプログラミングでも、worked example の優位は経験とともに消えた（[Kalyuga 2007](https://www.uky.edu/~gmswan3/EDC608/Kalyuga2007_Article_ExpertiseReversalEffectAndItsI.pdf)）。PR のレビュアーの多くはそのコードベースの熟練者なので、「全部を丁寧に説明する」既定値は逆効果になりうる（推論）。

LLM 時代の測定は、ここに否定的な証拠を加えた。Copilot で生成した説明を付けた PR は、レビュー時間が短く、マージされやすかった（[Xiao, 畑, Treude, 松本 FSE 2024](https://arxiv.org/abs/2402.08967)）。Qodo ベースの bot のコメントは 73.8% が「resolved」（対処済み）とラベル付けされた一方で、PR のクローズまでの平均時間は 5 時間 52 分から 8 時間 20 分に延びた。延び方はプロジェクトによって違った（[Cihan ほか](https://arxiv.org/abs/2412.18531)。本文で確認し、「受け入れられた」から訂正）。Tufano らは 29 人の専門開発者の統制実験で、生成レビューを出発点にするとレビュアーが指摘箇所に集中して他の箇所を探さなくなり、時間も自信も改善しないと報告した（[arXiv 2411.11401](https://arxiv.org/html/2411.11401v3)、本文で確認）。Shen と Tamkin の 52 人の RCT では、AI を使った群の理解テストは 50% で、手書き群の 67% を下回った。完了時間に有意差はなかった（[Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)、本文で確認）。産業研究の成果変数は、ほぼすべて解決率・マージ・時間である。**レビュアーが変更を理解したかを測った産業研究は見つからなかった**。

## 作り手の意図と気付きは、信頼・鮮度・読者の損得に集中している

測られた事実とは別に、作り手が失敗や観察から得た気付きは、ツールの信頼をどう保つかに集中している。Baum の 6 原則は、関連する変更部分を近くにまとめること、必要になる前に情報を出すこと、最も近い距離は同時に画面に見えていることだとする。そして、まとめ方を読者に見える規則にすることを求める（「making the grouping explicit to the reviewer」、[Baum 2017](https://tobiasbaum.github.io/rp/optimalordering.pdf)）。呼び出し関係の向きは人によって分かれ、調査では 85% が呼ばれる側からを好んだが、面接では呼ぶ側から派も多かった。pr-tour の SKILL.md はこれを実装に移している。step 間の遷移を必須にし、未検証のつながりには `inferred` と具体的な不確かさを付け、実行順でない並べ替えには `reading` と印を付ける。`source` 引用は「自動で証明された呼び出し辺ではなく解釈の記録」だと明記している（[SKILL.md](https://github.com/YunSinLee/pr-tour/blob/main/skills/pr-tour/SKILL.md)）。

**鮮度と再読** の発想は、ツアー系よりレビューツールの側で成熟している。Iron の Minsky は「Humans are bad at carefully thinking about boring things」と書き、レビュアーには前回見た版からの差分だけを読ませ、衝突したマージは diff-of-diffs で示した（[Jane Street](https://blog.janestreet.com/code-review-that-isnt-boring/)）。Reviewable は、誰がどのファイルのどのリビジョンを読んだかを追跡する（[docs](https://docs.reviewable.io/)）。ツアー系でこれに相当する仕組みを持つのは balade だけで、PR 番号とコミット SHA を記録し、head が進むと stale を表示する（[balade](https://github.com/basaltbytes/balade)）。Swimm の Auto-sync は、コードの移動を決定木で判定し、自信がなければ人に選び直しを頼む（「We'd rather ask you to reselect a snippet than offer a strange suggestion.」、[Swimm](https://swimm.io/blog/how-does-swimm-s-auto-sync-feature-work/)）。

**信頼はノイズと省略で失われる**。Greptile が自社の AI レビューのコメントを監査すると、良いものは約 19%、nit が 79% だった。LLM に重大度を採点させる方法はほぼランダムで、チームごとに過去に downvote されたコメントに似たものを止める方式に変えると、対処率は 2 週間で 19% から 55% 超になった（[Greptile](https://greptile.com/blog/make-llms-shut-up)、自社の数字）。CodeRabbit は自社のブログで、AI コメントを PR スレッドに足すとかえって認知負荷が増えると認めている（[Change Stack](https://www.coderabbit.ai/blog/introducing-change-stack-the-first-ai-native-code-review-interface)）。SemanticDiff は「Developers will only use a diff/code review tool if they can trust it」として、意味を変えうる変更を既定で隠さない（[SemanticDiff](https://semanticdiff.com/blog/language-aware-diff-how-far/)）。Google の Tricorder も同じ考えで設計されている。以前のツールは誤検知が多く対処できない結果を出し、FindBugs をレビューに出した試みも、結果の遅れと対処されない結果の多さでほとんど使われなかった。そこで Tricorder は「NOT USEFUL」ボタンで「役に立たない」率を監視し、10% 以上になった解析を保護観察に置く。著者は、出力を理解できないと信頼はすぐ失われるとも書いている（[Tricorder](https://www.cs.umd.edu/class/spring2019/cmsc414/papers/tricorder-building-a-program-analysis-ecosystem.pdf)。本文で確認し、「誤検知のためにツール全体を信頼しなくなった」から訂正）。

**読者は損得を計算する**。CodeTour の利用研究で、バグを直したいだけの参加者は、ツアーは読むコストに見合わないと判断した。ツアーに従った群は無関係なファイルを開かなかったが、開いたファイルの数自体も少なく、著者は「ツアーにない部分は重要でない」と思わせることを懸念した。ツアーの品質は書き手次第だった（「CodeTour's usefulness is limited by the authors' ability to share helpful annotations」、[Taylor & Clarke PPIG 2022](https://ppig.org/files/2022-PPIG-33rd-taylor.pdf)）。Cursor は非常に大きい PR にはツアーを出さない（[Cursor docs](https://cursor.com/docs/origin/code-tours)）。Python Tutor の Guo は、「黒板に収まらないコードは可視化に向かない」と範囲を決めた。インストール不要、オプション最小、URL で状態ごと共有するという 10 の指針で成功したと振り返っている（[Guo UIST 2021](https://par.nsf.gov/servlets/purl/10309256)）。

tools for thought の系譜は、説明の **形** について気付きを残している。Victor は「Visualize data, not code.」「We understand data by comparing it to other data.」と書き、抽象と具体の往復に洞察が生まれるとした（[Learnable Programming](https://worrydream.com/LearnableProgramming/)、[Ladder of Abstraction](https://worrydream.com/LadderOfAbstraction/)）。pr-tour は流れ順と定義プレビューを持つが、変更前後の値や振る舞いの比較は持っていない。系譜から見て最も欠けているのはここである（推論）。Gîrba は、汎用ツールは実践では効かないとし、問いごとのビューは数分で作れて一度しか使われないことが多いと書いた（[InfoQ](https://www.infoq.com/articles/moldable-development/)）。LLM が使い捨てのビューを作るコストを下げた今、この主張は PR ごとのツアーを正当化する。ただし feenk 自身は効果の定量的な証拠を示していない。Litt は「Chat is an essentially limited interaction mode, regardless of the quality of the bot.」と書き、LLM の出力は利用者自身の構造的な理解で監査すべきだとした（[Litt 2023](https://www.geoffreylitt.com/2023/03/25/llm-end-user-programming)）。

pr-review の共有メンタルモデルには、3 つの研究がつながる。LaToza らは、暗黙知は設計文書ではなく対面の会話とコードで共有されると報告した（[MSR](https://www.microsoft.com/en-us/research/?p=154508)、[本文](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/p492-latoza.pdf)で確認）。Spadini らによれば、既存のレビューコメントは判断を偏らせる「プライマー」ではなく、普段見落とす種類の欠陥を思い出させる「リマインダー」として働く（[ICSE 2020](https://2020.icse-conferences.org/details/icse-2020-papers/17/Primers-or-Reminders-The-Effects-of-Existing-Review-Comments-on-Code-Review)、[本文](https://sback.it/publications/icse2020.pdf)で確認）。CRCM によれば、レビュアーは仕様・実装・注釈の 3 層のメンタルモデルを作り、実際の変更を「予想した解」や「理想の解」と比べる（[Wurzel Gonçalves ほか](https://arxiv.org/html/2503.21455v1)）。

## 捨てられたものは、作るコスト・一般化・隠しすぎ・ノイズで止まった

「理解支援が役に立たなかった」と正面から書いた事後分析は、製品側には一つも見つからなかった。公表された終了理由は、プラットフォームによる吸収、会社の戦略、または無言である。研究と個人の振り返りからは、もっと具体的な失敗の型が読み取れる。

| Phacility（Phabricator） | 2021 年に終了 | 理由は書かれていない（[Phacility](https://admin.phacility.com/phame/post/view/11/phacility_is_winding_down_operations/)） | — |

これらは 4 つの型にまとまる。1 つ目は **説明 1 本あたりの作者のコスト**（Distill、literate programming、CodeTour の「書き手次第」）である。2 つ目は **一般化しすぎ**（Subtext。Guo の言葉では「trying to be too general actually hinders scale and sustainability」、[Matuschak の抜粋](https://notes.andymatuschak.org/zVxPT5mYfnUZBWxMYSaTf7H)）である。3 つ目は **アルゴリズムで定めた「関連」と、人が必要とする範囲のずれ**（Flowistry、CodeTour、自動デバッグ）である。4 つ目は **ノイズによる信頼の喪失**（FindBugs、AI レビューの nit）である。LLM はこのうち 1 つ目のコストを大きく下げた。しかし 3 つ目と 4 つ目は、むしろ強めうる。AI のツアーは、より多くの PR で、より自信ありげに、注意を誘導するからである（推論）。

## 設計原理の候補は、証拠の強さで 3 段に分かれる

上の資産と失敗から、pr-tour と pr-review に移せる原理の候補を、証拠の強さで分けた。A は人で測られた事実に基づくもの、B は作り手の意図や理論にとどまるもの、C は失敗から逆算したものである。どの原理も、PR ツアーや下書き支援に当てはめた効果は測られていない。

|---|---|---|---|

| C | 差し込む情報の「役に立たない」率を測って削る | [Greptile](https://greptile.com/blog/make-llms-shut-up)、[Tricorder](https://www.cs.umd.edu/class/spring2019/cmsc414/papers/tricorder-building-a-program-analysis-ecosystem.pdf) | 下書きの採用率・却下理由を記録し、チームごとに抑制する |
| C | 範囲を絞り、walk-up-and-use にし、一度に発明しすぎない | [Guo 2021](https://par.nsf.gov/servlets/purl/10309256)、[Edwards](https://www.subtext-lang.org/retrospective.html) | 大きすぎる PR では出さない（Cursor）。新機能を一度に足さない |
| C | 自動化で対人の知識共有を消さない | [CRDM](https://arxiv.org/abs/2507.09637)、[Storey](https://margaretstorey.com/blog/2026/02/09/cognitive-debt/) | 下書きは人が判断する。誰が理解したかを残す |

原理どうしには **衝突** がある。1 つ目は網羅と熟達化反転の衝突で、全変更を網羅して説明する pr-tour の方針は、熟練者には冗長になる。解き方の候補は、網羅は一覧と印で保証し、説明の量だけを読者に合わせることである（推論）。2 つ目は Gîrba の「問いごとに多くのビュー」と Guo の「範囲を絞る」の衝突である。普及の証拠があるのは Guo の側だけだ。3 つ目は順序の衝突で、ツアーが順序を決めること自体が、Tufano らが見たアンカリングと同じ種類の注意誘導になる。順序の効果は確かめられていない一方で、順序の副作用（後ろの見落とし、探索の減少）は測られている。

**評価の原理** は独立して重要である。de Jong は、germane load（学習に役立つとされる負荷）の説明が事後的で、「what is good is good, what is bad is bad」という同語反復になっていると批判した（[de Jong 2010](https://ris.utwente.nl/ws/files/6597420/Jong10cognitive.pdf)）。Fakhoury らの研究では、自己報告と fNIRS と注視時間が互いに相関しなかった（[NSF PAR](https://par.nsf.gov/servlets/purl/10135165)、本文で確認）。「わかりやすかった」というアンケートは、理解の指標として弱い。測るべきなのは、効果が出やすいと報告された指標を別々に見ることである。具体的には、誤指摘の数、後半のファイルの見落とし、変更の理由を後から説明できるか、事後に影響範囲を答えられるか、の 4 つである。Meta が速度の指標と並べて Eyeball Time をガードレールにしたことは、速度だけを最適化しないための先例になる（[Meta](https://engineering.fb.com/2022/11/16/culture/meta-code-review-time-improving/)）。

## 未確認事項は、効果の測定と一次資料の欠落に集中している

最大の未確認事項は、**PR ツアー（読む順番と説明の提示）がレビュアーの理解や欠陥発見を改善するかを測った対照実験が、一つもないこと** である。CodeRabbit の「約 20 分の把握が約 30 秒に」は 1 事例の逸話にすぎない。PPIG 2022 は小規模で、統計的に有意ではない。AI の説明が誤っているときにレビュアーがそれを見抜く率（過信）の定量研究も見つからなかった。仕様書や設計判断など、コード以外の高負荷な成果物の理解支援についても、今回の人物群から直接の資料は得られていない。

## 結論

この調査で理解が変わった点は 2 つある。1 つ目は、**並べ方は理解支援の中心ではなく、注意の配分の道具だ** ということである。流れ順や依存順のツアーは、2026 年にはどの製品でも同じ形に収束した。しかし、その効果を最も真剣に測った Baum 本人が、効率の改善を確かめられなかった。確かに効くと分かっているのは、「なぜ」を最初に出すこと、離れた関係を同時に見せること、後ろに回したものを隠さないことである。pr-tour が差別化できる余地は順序そのものではない。推論と検証済みの区別、ツアーの外側の明示、PR が更新されたときの再読、変更前後の振る舞いの比較、といった手薄な部分にある。

2 つ目は、**LLM が作者のコストを消したことで、ボトルネックが「説明を作ること」から「人が実際に考えたかを保つこと」へ移った** ということである。先行者の失敗の多くは説明を作るコストで止まったが、今はそのコストがほぼゼロになった。その代わりに、アンカリング、受け身の委任、ノイズによる信頼の喪失、作者自身も説明できない変更が、測られた問題として現れている。pr-review の「人が判断し、チームの共有メンタルモデルを育てる」というゴールは、Storey の cognitive debt をちょうど裏返したものであり、先行研究で最も裏付けの薄い、いちばん価値のある場所に立っている。自分の仕組みを作るなら、効果を「解決率と時間」ではなく、事後に意図と影響範囲を説明できるかで測る評価を最初から組み込むこと。それが、この分野にまだない最初の証拠になる。
