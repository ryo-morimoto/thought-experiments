# te の骨格は既存標準と一致し、欠けは5点

**結論**: te の骨格はほぼすべて既存の標準や先行事例と一致する。追記だけの出来事の列、対立仮説を操作で消す構造、文脈を持たない reviewer、結論の前提へのラベル付けがそうだ。Fowler の Event Sourcing、ADR（MADR・Nygard）、Heuer の ACH、IBIS、AIF、英国防省の Red Teaming Handbook、ICD 203 は、それぞれ te の一部と同じ形を独立に持っている。だから標準を「形式」として取り込む必要は小さい。取り込む価値が高いのは、te に欠けている概念である。調べた範囲で、欠けているものは次の5点になる。(1) 反論が前提・推論・結論のどれを攻撃するか（ASPIC+ の undermine / undercut / rebut）。(2) 対立仮説ごとに「何が出たら捨てるか」を事前に書く欄（敵対的共同研究、Registered Reports）。(3) 予測を対立仮説ごとの確率で書き、事後に採点できる形（Good Judgment Project の Brier スコア、Baldi & Itti の驚き）。(4) 結論に受け入れる短所と置き換え（`supersedes`）を書く欄（Nygard、Y-statement）。(5) 前提が誤っていたときの影響を書く欄（ICD 203 の linchpin 仮定）。形式として採る価値があるのは JSON Lines（正本）、JSON Schema 2020-12（出来事の形）、Argdown（MIT、`te render` の書き出し先）の3つに限られる。RO-Crate・CloudEvents・PROV-O・AIF は、正本にはせず、対応表か片方向の書き出しにとどめる。GRADE の4段階、NUSAP の pedigree matrix、Micropublications・nanopublications・ORKG の RDF/OWL 系は、単独利用者のファイル型ツールには重すぎる。注意点もある。ACH は実験的な評価で確証バイアスを減らすと示されておらず、判断の不整合を増やしうる（[Dhami ほか 2019](https://strathprints.strath.ac.uk/69049/)）。したがって te は、行列の採点で自動判定をせず、記録と検査に使うのが安全である。

## 論証の標準は te の出来事に一対一で写り、undercut だけが表せない

論証構造の標準を te の出来事に当てると、対応はほぼ一対一になる。IBIS は Kunz と Rittel が1970年に考案した記法で、issue・position・argument の3種のノードを持つ（[Wikipedia: IBIS](https://en.wikipedia.org/wiki/Issue-based_information_system)）。それぞれ te の問い（`experiment.toml`）、`rival`、`operation` の `favours` / `eliminates` に当たる。ただし IBIS には、対立仮説を消す概念も、本命の逆を必ず置く規則もない。この点で te は IBIS より強い。IBIS の実装である Compendium は最終リリースが 2014 年で、保守されていないとされる（[Wikipedia ミラー: Compendium](https://www.wikiwand.com/en/articles/Compendium_(software))）。取り込めるのは語彙だけで、地図（maps/）の問いの入れ子に合う。

**AIF**（Argument Interchange Format）は、命題（I-node）どうしを直接つながず、推論 RA・衝突 CA・選好 PA の中間ノードを必ず介す（[AIF Specification 2011](https://arg-tech.org/wp-content/uploads/2011/09/aif-spec.pdf)）。te では `eliminates` を `operation` の欄としてしか書けないので、「rival を消すときは、どの操作で消したかを必ず残す」ことになる。これは AIF の原則と同じ不変条件で、te はすでに満たしている。AIF は RDF/OWL 系なので、標準ライブラリだけで書く te.py の正本には向かない。需要が出たときに `te render` の片方向の書き出しにすれば足りる。参照実装の OVA3 は archived で、LICENSE ファイルがない（[GitHub: arg-tech/ova3](https://github.com/arg-tech/ova3)）。

te に足りないのは、反論が「何を」攻撃するかの区別である。**ASPIC+ は、論証への攻撃を前提への undermining、結論への rebutting、推論規則への undercutting の3つに分ける**（[Modgil & Prakken, ASPIC+ tutorial 2014](https://dspace.library.uu.nl/bitstream/handle/1874/304259/ASPICtutorial.pdf?sequence=1)）。Argdown も記法で attack（`-`）と undercut（`_`）を分ける（[Argdown Syntax](https://argdown.org/syntax/)）。Toulmin の rebuttal も、形式論証の研究では undercutter（推論への攻撃）と読まれる（[Verheij 2009](https://www.ai.rug.nl/~verheij/publications/pdf/toulmin2009.pdf)）。Prakken らの解釈は検索要約経由で、本文は未確認である（[Prakken ほか COMMA 2026](https://webspace.science.uu.nl/~prakk101/pubs/comma26TAL.pdf)）。te の `attack.objections` は `premise` 欄しか持たないので、undermine しか表せない。思考実験でいちばん起きやすい undercut は「前提は正しいが、思考実験で再現した変化が現実の判断に効くという橋渡しが成り立たない」という型の攻撃で、これを記録する欄がない（推論）。te の応答の型（surrender / bar / restrict / reinterpret / incorporate）は「攻撃を受けてどう修復するか」の分類で、ASPIC+ の「何を攻撃するか」とは直交する。両方を持つのが正しい。応答の型が Lakatos『Proofs and Refutations』に由来するかは、未確認である。

**Carneades** は、命題ごとに証明基準（proof standard）を割り当て、pro と con の論証から受理を計算する。基準は強い順に次の3つである（[Gordon, Prakken, Walton 2007](https://tfgordon.github.io/publications/GordonPrakkenWalton2007b.pdf)）。DV（Dialectical Validity）は、defensible な pro が1つ以上あり、defensible な con が1つもないこと。BA（Best Argument）は、ある pro がすべての con より優先すること。SE（Scintilla of Evidence）は、pro が1つでもあること。このうち DV は te の「脱落」の判定に最も近い。`conclusion.options.status` を手で書く代わりに、`rules.toml` の述語にして `fold` で計算する根拠になる。Carneades は前提を ordinary・assumption・exception にも分ける。この分け方は te の `label`（証拠の種類）と直交する軸で、`attack` の bar（例外として除く）に対応がつく。実装の carneades-4 は MPL-2.0 で、最終コミットは 2024-10 である（[GitHub: carneades-4](https://github.com/carneades/carneades-4)）。コードは採らず、3つの基準の定義だけを借りればよい。

**ACH**（Heuer の対立仮説の分析）は8段階からなり、te の段階 A〜C にそのまま写る（[Heuer, Psychology of Intelligence Analysis ch. 8](https://www.cia.gov/resources/csi/static/Pyschology-of-Intelligence-Analysis.pdf)）。仮説×証拠の行列は `rival` × `operation` に当たる。「すべての仮説と整合する証拠は診断価値がない」は、`eliminates` が空の operation への警告になる。「反証しようとする」は、DV 型の判定に当たる。「少数の要の証拠への感度分析」は、`attack` で linchpin を名指しすることに当たる。「退けた仮説とその理由を論じなければ判断は不完全」は、`options[].reason` を必須にすることに当たる。ACH の段階8「将来の観察の目印（milestones）」には、te の欄がない。ただし評価の結果は厳しい。分析官50人の無作為化実験では、ACH 群は全段階を守らず、確証バイアスの軽減は混在した結果で、判断の不整合と誤差が増えうると報告された（[Dhami ほか 2019](https://strathprints.strath.ac.uk/69049/)）。一方で、行列の向き（仮説を行にする）を変えると確証バイアスが減ったという報告もある（[Dhami ほか 2024](https://link.springer.com/article/10.1186/s41235-024-00560-y)、検索要約経由で本文は未確認）。ここから言えるのは、形式を課すだけでは判断はよくならない、ということである。te は ACH のマイナスの数え上げを自動の判定に使わず、検査（診断性のない操作、退けた理由の欠落）にとどめるべきだ。

## 前提のラベルは外部標準と直交し、借りるべきは「度合い」の語彙

te の5ラベル（`definitional` / `argued` / `empirical-checked` / `empirical-unverified` / `value`）は「根拠の種類と確認状態」の軸である。GRADE・IPCC・ICD 203 は、いずれも「確かさの度合い」の軸を扱う。両者は直交するので、置き換えるのではなく、必要なら任意の欄として足すのが正しい。

**ICD 203** は、te のラベル体系の外部の裏づけになる。この文書は、基礎となる情報を伝える文と、仮定・判断を伝える文を明確に区別するよう求める。さらに、論の要（linchpin）の仮定を明示し、仮定が誤っていたときの影響を説明するよう求める（[ICD 203](https://archive.dni.gov/files/documents/ICD/ICD-203.pdf)）。これは te の `empirical-*` と `argued` / `value` の区別と同じ発想である。ここから、前提に `if_false`（崩れたら結論はどう変わるか）の欄を足す根拠が得られる。同じ文書は、確信度と尤度を同じ文で組み合わせることを禁じ、尤度の言葉を7段階で固定している。たとえば likely / probable は 55–80% である（[ICD 203](https://archive.dni.gov/files/documents/ICD/ICD-203.pdf)）。

**IPCC AR5 の不確実性ガイダンス**も、確信度（根拠×合意、定性的）と尤度（確率）を別の尺度に分け、「確信度を確率として解釈してはならない」と明記する。根拠は limited / medium / robust、合意は low / medium / high の語で要約する（[Mastrandrea ほか 2010](https://www.stat.berkeley.edu/users/aldous/157/Papers/ipcc_uncertainty-guidance-note.pdf)。IPCC の原本は取得時 403 だったため、ミラーから読んだ）。さらに「about as likely as not を知識の欠如の表現に使ってはならない」とも書いている。ただし likely の境界は IPCC では 66–100% で、ICD 203 とずれる。te が確率を言葉で書くなら、どちらの表を使うかを `rules.toml` で固定するか、数値で書かせるべきである。ここから te に効く規則は次の3つになる。`prediction.confidence` には確率だけを入れる。根拠の質は別の欄に書く。知らないことを 50% と書かない。AR6 で尺度が変わったかは未確認である。

**GRADE** は、研究デザインで出発点を決めて、5つの観点で下げ、3つの観点で上げる4段階の方式である（[GRADE Handbook](https://gdt.gradepro.org/app/handbook/handbook.html)）。20か国以上の120を超える組織が支持または使用している（[GRADE Working Group](https://www.gradeworkinggroup.org/)）。ただし単位は「介入の効果推定」で、te の前提（政策の数値、制度の事実）とは対象が違う。また Handbook の転載には許可が要り、オープンライセンスは明示されていない。借りるべきは段階名ではなく、下げる観点の語彙である。特に GRADE の indirectness と GRADE-CERQual の relevance（データが問いの文脈にどれだけ当てはまるか、[Lewin ほか 2018](https://pmc.ncbi.nlm.nih.gov/articles/PMC5791044/)）がそうだ。これらは te が実際に起こした「別の文脈の数値の流用」を名指ししている。前提に任意の `concerns = ["indirectness"]` を足せば、「一次資料だが文脈がずれる」を `empirical-checked` のまま記録できる。**NUSAP**（値・単位・幅・評価・来歴）は `outputs/` の数値の記述に向くが、出典は Wikipedia だけで、一次資料は未確認である（[Wikipedia: NUSAP](https://en.wikipedia.org/wiki/NUSAP)）。pedigree matrix の採点は単独利用者には重い。`value` と `definitional` に当たる段階は、どの標準にもない。この2つは te 独自の部分として残す理由がある。

出典と来歴の語彙では、**W3C PROV-O**（2013年の勧告）の最小部分がいちばん素直に写る（[W3C PROV-O](https://www.w3.org/TR/prov-o/)）。`by` は Agent に当たり、`claude` は SoftwareAgent、`user` は Person になる。出来事は Activity、`sources.toml` の1件と `outputs/` の1ファイルは Entity に当たる。一次資料は hadPrimarySource、引用文は wasQuotedFrom、`correction` は wasRevisionOf に対応する。ここから te に足す価値が最も高いのは、二次資料の `primary_of`（= hadPrimarySource）である。この欄があれば、「孫引きを見つけたが一次はまだ取っていない」状態を記録できる。そして `checked-needs-primary` の違反メッセージで、一次資料の候補を示せる。**CiTO**（CC BY 4.0、版 2.9.2）は、引用の性格を表す語を持つ。supports、disputes、usesDataFrom、citesAsEvidence、qualifies などである（[CiTO](https://sparontologies.github.io/cito/current/cito.html)）。前提→出典の結びつきに `role` として5〜6語だけ借りれば、反対の証拠を探した記録（`disputes`）を前提ごとに残せる。Micropublications（[arXiv:1305.3506](https://arxiv.org/abs/1305.3506)）の「主張・支持・反論のグラフ」は、te の `premises` と `objections` の組と同じ形である。nanopublications の「主張 / 主張の来歴 / 記録の来歴」の3部構成（[nanopub.net guidelines](https://nanopub.net/guidelines/working_draft/)）も、te の結論・前提と出典・`by` と `at` の分け方と一致する。どちらも te の設計が先行研究と同じ形にたどり着いたことの確認には使える。しかし、OWL・署名・分散サーバーを取り込む利点はない。ORKG と schema.org の ClaimReview は、Web 公開や論文比較のための仕組みで、内部の記録には向かない。

## 段階の規則には Tetlock・赤チーム・事前登録の手順がそのまま入る

思考実験の「標準の分類」は存在しない。SEP は、目的による分類、Sorensen の論理構造による分類、Brown の破壊的／構成的の分類を並べるが、どれも標準とは呼ばない。Brown の分類にも「異論がないわけではない」と注記している（[SEP: Thought Experiments](https://plato.stanford.edu/entries/thought-experiment/)）。最も広く参照される Brown の区分は、te の「破壊・構成」と一致する。Brown は破壊的な思考実験を4つに分ける。内部矛盾を暴くもの、他の信念と衝突させるもの、中心の前提を崩すもの、反例である（[SEP](https://plato.stanford.edu/entries/thought-experiment/)）。これを `frame.mode` の副欄にすると、確認すべきことが決まる。たとえば内部矛盾なら、無矛盾性を確認する。構成的の下位区分（媒介的・推測的・直接的）は、二次資料経由でしか確認していない（[El Skaf 2021](https://link.springer.com/article/10.1007/s11229-021-03063-1)）。El Skaf は、物理の思考実験の多くが破壊と構成を兼ねると論じる。これは `mode` を1つに限る今の設計への反例になる。`modes_not_picked` を残す今の形は妥当だが、複数のモードを選べるようにする余地がある。SEP は「反例の思考実験は、効果を持つためにそれほどもっともらしい必要はない」とも書く。これは、reviewer の反例を「非現実的だから」の一言で退けさせない規則の根拠になる。

段階 A・B の手順に最も直接に使えるのは、Tetlock & Belkin（1996）の反事実の評価基準である。1つは「明確さ」で、思考実験は1度に1つの原因を操作すべきだとする。もう1つは「共立可能性」で、前件と後件をつなぐ原理が互いに、また前件と両立することを求める（[Turku 大学ブログの解説](https://blogit.utu.fi/futuresofscience/2020/09/18/squeezing-water-out-of-stones-on-historical-counterfactuals/)、二次資料経由。書誌は [CASBS](https://casbs.stanford.edu/counterfactual-thought-experiments-world-politics-logical-methodological-and-psychological)）。前者は `operation.varied` を1つに限る検査に、後者は `frame.flaw` の確認項目（固定した条件・理想化・変えた条件が互いに矛盾しないか）として `show` に入れられる。

**英国防省 Red Teaming Handbook**（第3版、2021年）は、te の段階 C と `te brief` の設計に、外部の根拠を与える（[Red Teaming Handbook](https://assets.publishing.service.gov.uk/government/uploads/system/uploads/attachment_data/file/1027158/20210625-Red_Teaming_Handbook.pdf)）。同書は、外部の red team の利点を次のように挙げる。計画に投資しておらず、成否に中立で、既存の偏りに影響されない。適した構成員は2種類で、分野の専門家と、分野を知らないが分析力のある非専門家である。後者は「新鮮で新しい視点」をもたらす。これは `brief` が経緯を構造上含まない設計と同じ理屈であり、`--lens` の既定の組を「専門家」と「非専門家」にする根拠になる。同書の pre-mortem の手順（失敗したと仮定し、直接の原因を2〜6個挙げ、制御できる決定点までさかのぼる）は、`brief` の依頼文の型に使える。「この結論が誤りだったと判明した。なぜか」と問う形である。前提の確認（assumptions check）は、段階 A の `show` に入る。悪魔の代弁者については、Schwenk（1990）のメタ分析が、専門家だけの方法より全般に効果的だったと報告している（[IDEAS/RePEc](https://ideas.repec.org/a/eee/jobhdp/v47y1990i1p161-176.html)）。ただし、独立した reviewer と自己批判を直接比べた研究は見つからなかった。te の「fresh は self より良い」は、仮説のままである。

te に最も欠けているのは、反証の条件を事前に決めることである。**敵対的共同研究**では、対立する当事者が反証の条件に事前に合意し、中立の仲介者を置き、方法と分析に合意したうえで事前登録する（[Clark の講演スライド 2022](https://nutrition.org/wp-content/uploads/2022/11/Clark_ASN_Adversarial-Collaboration.pdf)）。論文は Clark, Costello, Mitchell, Tetlock（2022, DOI 10.1037/mac0000004）だが、本文は未取得である。**Registered Reports** の Stage 1 は、結果を見る前に、問いの重要性と仮説の論理を審査する（[PNAS Nexus Guidelines](https://academic.oup.com/pnasnexus/pages/registered-reports-guidelines)）。te の段階 A の `requires` に `prediction` があるのは、この考え方と一致する。ただし、次の2つが欠けている。(a) `rival` に `would_reject_if`（何が出たら捨てるか）を持たせ、段階 A の必須にすること。(b) 最初の `operation` の後には `prediction` を訂正できない、という不変条件。この2つがあれば、段階 C の結論が後付けの解釈になるのを、構造で防げる。

価値の確認3点は、外部の基準と別々の軸に対応する。(1) 先行する答えは新規性に当たる。NIH の革新性は「現在の研究や臨床実践の枠組みに挑み、変えようとするか」を問う（[NIAID Review Criteria](https://www.niaid.nih.gov/research/review-criteria)）。(2) 実在の保持者は、意義に当たる。(3) 実務者の予想との比較は、驚きに当たる。Baldi と Itti は、驚きを「事前と事後の信念分布の距離」と定義した（[PMC2860069](https://pmc.ncbi.nlm.nih.gov/articles/PMC2860069)）。NIH の指針は「革新的でなくても重要な研究がある」とする（同ページ、検索要約経由）。CSR も、従来の方法が適切なら革新性で減点すべきでないと論じる（[CSR Review Matters](https://www.csr.nih.gov/reviewmatters/?p=131)）。したがって、先行する答えが見つかっても実験を自動で止めず、利用者の `decision` で続けるかを決める今の形は正しい。3点は1つの合否にまとめず、軸ごとに記録するべきである。予想の比較を感想から数値にするには、`prediction` を対立仮説ごとの確率の配分にする必要がある。Good Judgment Project は100万件を超える予測を Brier スコアで採点した（[Mellers, Tetlock ほか](https://scholar.harvard.edu/sites/scholar.harvard.edu/files/rzeckhauser/files/improving_the_accuracy_of_geopolitical_risk_assessments.pdf)）。この形なら、`fold` が Brier スコアと事前・事後の距離を計算できる。同じプロジェクトでは、参照クラスの訓練が正確さと相関した（[AI Impacts](https://aiimpacts.org/?p=1283)、二次資料）。これは、`prediction` に参照クラス（似た問いで分野がどう答えたか）を書かせる指示の根拠になる。

## 記録の形式は Event Sourcing と ADR の実務に合わせ、梱包標準は派生物に回す

te の記録は、**Fowler の Event Sourcing**（「すべての状態の変化を出来事の列として捕らえる」）と同じ形である。訂正は、上書きではなく新しい出来事で表す（[Fowler](https://martinfowler.com/eaaDev/EventSourcing.html)）。実務でいちばん問題になるのは、スキーマの進化である。Overeem ら（JSS 2021）は、19のイベントソーシングの系を調べた。そして、最初は versioned events と weak schema で始め、必要になってから upcasting や copy-and-transform に進むよう勧めている（[arXiv:2104.01146](https://arxiv.org/abs/2104.01146)、検索要約経由で本文は未読）。「出来事は決して変えない」と言う人は多かったが、実際に守っていた人はほとんどいなかったという報道もある（[InfoQ 2018](https://www.infoq.com/news/2018/02/evolving-cqrs-event-sourcing/)）。te では、各出来事に `v` を書き、`fold` の手前に純粋関数 `upcast(event)` を挟むのが、この順路に合う。Fowler は、外部への問い合わせが再生のたびに変わりうる問題を挙げ、対策の1つに「応答を記録して再生に使う」を挙げる。`te source add` が sha256 と取得日を記録するのは、まさにこれに当たる。`te check` が URL を取り直して差分が出たときは、「外部が変わった」として、記録の誤りと区別して報告するべきだ。

**JSON Lines** の要件は、UTF-8、1行に1つの JSON 値、`\n` 区切りの3つだけである。用途としてログとパイプラインを挙げている（[jsonlines.org](https://jsonlines.org/)）。媒体型 `application/jsonl` は、まだ標準化されていない。**CloudEvents** は CNCF の Graduated 仕様で（2024-01-25、[CNCF](https://cncf.io/announcements/2024/01/25/cloud-native-computing-foundation-announces-the-graduation-of-cloudevents)）、必須の属性は `id`・`source`・`specversion`・`type` の4つである（[CloudEvents spec](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md)）。ただし準拠すると、各行に `specversion` と `source` が繰り返され、固有の欄が `data` の下に1段下がる。1ファイルに追記する te では、読みにくさが増えるだけである。採るべきなのは、CloudEvents の設計判断のほうだ。外枠と本体を分け、id の一意性の範囲を「実験ディレクトリ内」と定め、時刻を RFC 3339 にし、スキーマの版を出来事に書く。CloudEvents をファイルへの永続化に使う公式の推奨は、見つからなかった。

**ADR** の要素は、te の出来事にほぼそのまま写る。MADR 4.0.0（2024-09、ライセンスは MIT OR CC0-1.0）の節は、Context、Decision Drivers、Considered Options、Decision Outcome、Pros and Cons、Confirmation である（[MADR](https://adr.github.io/madr/)）。これらは順に、`frame`、ゴール、`rival`、`conclusion`、`favours` / `eliminates` / `objections`、`te check` に当たる。te に欠けているのは2点である。1つめは、Nygard の「良いものも悪いものも、すべての帰結を書く」に当たる欄（[Nygard 2011](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)）。Y-statement の「受け入れる短所」も同じ要素である（[Zimmermann](https://medium.com/olzzio/y-statements-10eb07b5a177)、雛形の文言は未取得）。2つめは superseded の関係である。Nygard は「決定を覆しても古いものは残し、superseded と印を付ける。番号は再利用しない」と書く。te の `correction` は誤りの訂正で、方針の変更とは意味が違う。両者を同じ出来事に入れると、`fold` が「誤りだった」と「考えを変えた」を区別できなくなる（推論）。

**RO-Crate** は、ディレクトリ直下に `ro-crate-metadata.json` を1つ置き、ルートに name・description・datePublished・license を書くだけで成り立つ（[RO-Crate 1.2](https://www.researchobject.org/ro-crate/specification/1.2/root-data-entity.html)）。来歴は CreateAction（instrument＝道具、result＝作られたファイル）で書く（[RO-Crate Provenance](https://www.researchobject.org/ro-crate/specification/1.2/provenance.html)）。したがって `te run` の1回は、Process Run Crate の型にそのまま写る。Python の ro-crate-py は Apache-2.0 である（[ro-crate-py](https://github.com/ResearchObject/ro-crate-py)）。ただし、license が必須なのは私的な実験には余計な欄で、JSON-LD を正本にすると二重管理になる。利点が出るのは、Zenodo に出して DOI を付けるときだけである。そのため、`te export --ro-crate` で派生物として生成する扱いが釣り合う。仕様文書のライセンスは未確認である。出来事の形の検査には **JSON Schema 2020-12** が現実的である（[json-schema.org](https://json-schema.org/specification)）。te.py は標準ライブラリだけで書くので、使うキーワードを type・required・enum・properties・additionalProperties に限って自前で検査する。全体の検査は、CI で外部の検証器に任せる二段構えにする。CUE は JSON Schema と相互に変換できるが、Go の道具が要る（[CUE](https://cuelang.org/docs/concept/how-cue-works-with-json-schema/)）。Frictionless Data Package は表形式のデータが中心で（[Data Package v2](https://datapackage.org/standard/data-package/)）、te の sources や outputs には合わない。JSON Schema の公式なライセンスは未確認である。

採用する標準と、te の要素への写像を次の表にまとめる。「欄」は出来事の JSON の欄、「規則」は `rules.toml` の述語か `show` の指示を指す。

優先順位は、スキーマの変更が小さく、既知の失敗に直接効くものから並べる。第1は、`v` と `upcast` である。後から足すと既存の出来事の移行が要るので、最小の版の前に入れる。第2は、`objections.target` と `rival.would_reject_if` である。前者は undercut を表せるようにし、後者は事後の解釈を防ぐ。どちらも §8 の手順2（既存の記録1本で検出を確かめる）の評価対象にできる。第3は、`prediction` を rival ごとの確率にすることと、「operation の後は prediction を訂正できない」不変条件である。第4は、`supersedes`、`accepted_downsides`、`if_false`、`primary_of`。第5は、DV 型の判定と、`te check` の診断性の警告。第6は、`te render --argdown` と MADR の節順。RO-Crate の書き出しは、公開の需要が出てからでよい。この順は筆者の判断で、既存の記録に当てて欄が足りるかは、まだ試していない。

取り込まないものと、その理由は次のとおりである。CloudEvents の外枠をそのまま採らないのは、1行ごとに冗長な属性が増え、配送の可能性しか得られないからである。RO-Crate・AIF・PROV-O・Micropublications・nanopublications を正本にしないのは、JSON-LD / RDF / OWL が標準ライブラリだけの方針と二重管理の点で重いからである。GRADE の4段階と NUSAP の pedigree matrix は、対象（効果推定）が違ううえ、複数人の採点手順が単独利用には重い。ACH の採点と AI co-scientist の Elo を自動判定に使わないのは、前者は実験で効果が示されず、後者は著者自身が独立した正解でないと断っているからである。Carneades・OVA・Compendium・Open Source ACH のコードを採らないのは、止まっているか、ライセンスが不明だからである。Kialo は1つの主張を根にした pro/con の木で、複数の rival を並べて消す te の構造に合わない。公開された交換形式も確認できなかった。

設計書 §9 の未決事項には、次のように答える。出来事の列を JSON Lines にするか TOML の配列にするかは、**JSON Lines** にする。追記が1行の付け足しで済み、git の差分で1出来事が1行に見え、書き込み途中の壊れた末尾行を検出でき、`jq` で扱える。人が読む面は生成物の README が受け持つ（[jsonlines.org](https://jsonlines.org/)、[Fowler](https://martinfowler.com/eaaDev/EventSourcing.html)）。`note` の上限は、長さを数で縛るより、長い Markdown を `notes/<id>.md` に分けて出来事からパスで参照する形がよい。JSON 文字列の中の `\n` のエスケープが読みにくさの原因なので、上限はその後に必要なら設ける（推論。根拠になる標準はない）。既存の Markdown の記録を移すかは、新しい実験から te を使い、既存の記録は §8 の評価用に1本だけ一回限りで移す。Overeem らの copy-and-transform を一回だけの移行に限る扱いで、追記だけの約束を日常の運用では守れる（[arXiv:2104.01146](https://arxiv.org/abs/2104.01146)）。CI が te.py をどう入手するかに直接答える標準は、見つからなかった。筆者の案は、プラグインの固定したコミットを取得し、使った te.py の版を出来事か生成物に記録することである。これは RO-Crate が SoftwareApplication に `version` を書かせるのと同じ考え方である（[RO-Crate Provenance](https://www.researchobject.org/ro-crate/specification/1.2/provenance.html)）。MCP サーバーに移すかどうかは、今回の調査では判断の材料が得られなかった。§8 の手順3の呼ばれる割合で決めるのが筋である。

## Conclusion

この調査でいちばん重要な発見は、te の設計が「新しい形式を発明する」段階を終えていることである。情報分析（ICD 203、ACH）、ソフトウェアの決定記録（ADR）、論証理論（AIF、Carneades）、イベントソーシングは、それぞれ独立に、te と同じ形にたどり着いている。これは te の骨格が妥当であることの外部の証拠になる。同時に、残る仕事が「形式の採用」ではなく「欠けた概念の補充」であることも示している。欠けている5点は、どれも事前に何を書いておくかという性質を持つ。何を攻撃したか、何が出たら捨てるか、どの確率を予想したか、何を短所として受け入れたか、前提が崩れたら何が変わるか。いずれも事後には書けない、あるいは事後に書くと意味を失う。だから、これらは散文の指示ではなく、`rules.toml` の `requires` と不変条件に置くべきである。

もう1つの含意は、標準の効果の証拠が、標準の普及に比べて薄いことである。ACH は普及しているのに、実験では効果が示されていない。独立した reviewer の優位も、悪魔の代弁者のメタ分析からの類推にとどまる。te が §8 の評価で「呼ばれる割合」だけでなく「既知の失敗を検出したか」を測るのは、この空白を自分の記録で埋める唯一の手段である。事前に書かせる欄（`would_reject_if` と確率の `prediction`）は、その評価自体を採点可能にする。この意味でも、優先して入れる価値がある。
