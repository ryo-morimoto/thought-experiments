# 閉包の境界を、手で選ばずに決める規則を作れるか

- 状態: 結論済み
- 開始: 2026-11-24
- 更新: 2026-11-24
- 関連: [plan/browser-semantics-soundness/TREE.md](../plan/browser-semantics-soundness/TREE.md)、[extract/README.md](models/site-isolation/extract/README.md)、[experiments/2026-11-22-sink-path-inventory.md](2026-11-22-sink-path-inventory.md)
- 木の節: browser-semantics-soundness/B2a、browser-semantics-soundness/B2d

## 問い

取り出しの閉包（415 算法）は、根の算法を手で選んで決めた。性質が読む値（作業の木の A1、B2c で決めるもの）を書く段から逆にたどる規則で閉包を決めると、手で選んだ閉包と比べてどう違うか。あわせて、中身が文書に入る経路の一覧（取得の呼び出しと再利用）を、その規則の閉包から作り直し、手で選んだ経路の再現率を測る。

問いの出し方（ユーザーの判断）: 作業の木の効きが高・中の節がなくなるまで進める（/goal）。Claude は、互いにぶつからない作業の束に分けて並行で進め、この記録はその束の 1 つ。

## 前提

- 経路の一覧の思考実験は段階B まで（取得の呼び出しは精度 94%、再利用は 8.6%）。
- 経路ごとの支配の条件の判定は、伏せた 2 つの経路を特定させないため、リポジトリに書かない。
- モード: 構成的。

対立仮説:

- R1 作れる。逆にたどる規則の閉包は、手で選んだ閉包を含み、差は説明できる。
- R2 作れない。逆にたどると、ほとんど仕様の全体になる（境界が意味を持たない）。
- R3 作れるが、他の仕様からの差し込みが境界の外に残る。

設定の欠陥: 性質が読む値の選び方そのものは、モデルの作者が決める。

## 条件を変える

subagent が規則を書き、HTML と Fetch の全体の算法（1,995）と、持ち主の定義の無い ol の段の塊（347）の上で閉包を計算し、手で選んだ閉包と比べ、その閉包の中で経路の一覧を作り直した（[boundary/](models/site-isolation/boundary/RESULTS.md)、closure-rule.txt、compare.tsv、paths.tsv）。経路ごとの支配の条件の判定は、どのファイルにも書いていない。筆者は報告を読んだ。

**規則 T**: 種は、モデルが読む概念を書く段を持つ節（全体で 80、うち欄か集まりを書くもの 43）。行き先は 7 つ（crossOriginIsolated と originAgentCluster の getter、document.domain の getter と setter、opener の getter と setter、取得の応答の引き渡し）。他の仕様へのリンクはたどらず、出口として数える。行き先と、欄を書く種から呼び出し元をたどるが、呼び出し元が種か取得の包みのときだけ越える。含めた呼び出し元の引数を作る節を足す。種・行き先・引数を作る節から、呼び出し先の閉包を取る（理由: モデルが読む値を書かない呼び出し元は、引数か「呼ぶか呼ばないか」を通してしか種に効かず、前者は引数を作る節で覆い、後者はモデルが既に量化している）。

- 出口: 外へのリンク 707（基礎の仕様へ 452、他の仕様へ 255）。255 のうち 136 は、手元では仕様を決められない相互参照（service worker への受け渡しを含む）。名を挙げない他の仕様に委ねる段が 4。他の仕様から HTML と Fetch への呼び込みは、手元の原稿が 2 つだけなので見えない。

- 再現率: 手で選んだ参照の経路 9 のうち 8（原稿の中の 8 のうち 7、原稿の外の 1 は出口の行として）。前の一覧の取得の呼び出し 48/48、厳密な再利用 31/41（76%）、入り直し 3/3、手だけの行 5/6。参照の経路の照合は、記録の公開の文から組み立て直した（元の一覧はリポジトリの外）。
- 見つからないもの: 「ユーザーエージェントは…してよい」の散文（参照の経路の 1 つ）、入れ物も変数も名指さない続きの段 10、復号した画像の写し、他の仕様の中の経路、仕様を決められない出口。

読み取れること:

- R1（作れる）が当たった。規則の閉包は手の閉包を含み、差はすべて説明できた。手の根が落とした行き先も拾った。
- R2（ほとんど全体になる）は当たらなかった（素朴でも 41%、T で 26%）。ただし大きさは止め方の規則に依る。
- R3（他の仕様からの差し込みが外に残る）も、R1 と並んで当たった。
- 根を手で選ぶことは無くなったが、書き先の概念の型、行き先の一覧、包みの名前の型、止め方は、なお筆者の選択。

## 結果を攻撃する

経緯を知らない subagent 2 体（形式手法、ブラウザの実装と仕様の編集）に、A2・C4・A1・C9・B2a と B2d・D2 の結論をまとめて攻撃させた（ユーザーの判断: 作業の木の高・中がなくなるまで）。形式手法の観点は記憶で論じ、ブラウザの観点は仕様の本文と PR を 2026-11-24 に確かめた。筆者は、モデルの性質が CHOOSE と Cardinality を使わないこと（CHOOSE は反例の証人の定義だけ）と、compose/ の契約に liveness が無いことを確かめた。

| 種がモデルの読む概念から来るので、閉包はモデルに相対的で循環する。行き先と止め方も自由な引数で、呼び出し元を 1 段広げると 28% 増える。手の閉包を含むのは過近似というだけ（形式手法） | 受け入れる | 境界は「モデルの読む概念と行き先を決めたときの規則の閉包」で、仕様だけからは決まらない。手で根を選ぶことは無くなったが、選択は概念と止め方に移った |

## 結論

閉包の境界は、モデルが読む概念を書く段と 7 つの行き先から逆にたどる規則で、手で根を選ばずに決められた（610 算法、手の 415 をすべて含む）。ただし境界は、概念と行き先と止め方の選択に相対的で、仕様だけからは決まらない（呼び出し元を 1 段広げると 28% 増える）。経路の一覧は、その閉包の中で機械的に作れ、再利用の精度は 50%、参照の経路の再現率は 9 のうち 8（取り逃しは散文の裁量）。

生き残った選択肢: R1 と R3。脱落: R2。

## 経過

- 2026-11-24 段階A。問いと対立仮説を置いた。
- 2026-11-24 段階B。種と行き先から逆にたどる規則で閉包を決めた（610 算法、手の 415 をすべて含む）。その中で経路の一覧を作り直し、再利用の精度は 8.6% から 50% に、参照の経路の再現率は 9 のうち 8 になった。
- 2026-11-24 段階C。攻撃を受けて、境界が概念と止め方の選択に相対的であることを結論に書いた。結論を出した。
