# ブラウザの直った欠陥の型から作った変異体を、これまでの観測は殺すか

- 状態: 結論済み
- 開始: 2026-11-24
- 更新: 2026-11-24
- 関連: [plan/browser-semantics-soundness/TREE.md](../plan/browser-semantics-soundness/TREE.md)、[experiments/2026-11-21-blind-origin-oracle.md](2026-11-21-blind-origin-oracle.md)（取り置きのバグの集め方）
- 木の節: browser-semantics-soundness/C9

## 問い

これまでの変異体はモデルの作者が選んだ。Chromium と Gecko で直った、隔離に関わる公開の欠陥（CVE や公開のバグ）から、欠陥の型（どの段をどう誤ったか）を集め、モデルとは独立な変異体と軸を作る。これまでの観測（observe、gen、gen2、redirect の observed.tsv）は、その変異体を殺すか。殺せない変異体は、どの軸の外にあるか。

問いの出し方（ユーザーの判断）: 作業の木の効きが高・中の節がなくなるまで進める（/goal）。Claude は、互いにぶつからない作業の束に分けて並行で進め、この記録はその束の 1 つ。

## 前提

- 欠陥は公開のものだけを使う。公開されていない欠陥は扱わない。
- 型の分類と、変異体への写し方は事前に決めてから集める（前の事前登録の教訓）。
- モード: 破壊的（観測の穴を見つける）。

対立仮説:

- R1 殺す。直った欠陥の型の多くは、作者の変異体と同じ所にあり、これまでの観測で殺せる。
- R2 殺せないものが多い。欠陥の多くは、軸の外（キャッシュ、プロセス、競合、拡張）にある。
- R3 変異体に写せない。欠陥の多くは、モデルの段の言葉で書けない（実装の構造の誤り）。

設定の欠陥: 公開の欠陥は直ったものに偏り、型の分類は 1 人の判定。

## 条件を変える

subagent が、集め方と型の分け方を先に RESULTS.md に固定してから、公開で直ったブラウザの欠陥を集め、型に分け、型から変異体を作り、これまでの 4 つの観測の集合で殺せるかを確かめた（[bugmut/](models/site-isolation/bugmut/RESULTS.md)、bugs.tsv、BugMutants.tla）。筆者は報告を読んだ。

**集め方**（固定した規則）: 前の事前登録の候補の表から、隔離・sandbox・opener・リダイレクト・COOP・COEP・CORP・オリジンに触れるもの（最大 25）、NVD の CVE の API の語の検索（COOP、COEP、CORP、crossOriginIsolated、SharedArrayBuffer、site isolation、origin-keyed、document.domain、opener、sandbox と iframe、redirect と origin、navigation と origin）。2018-01〜2026-11、Chrome・Firefox・Safari を名指し、隔離の境界を名指すもの、記憶の安全性だけのものは除く。上限 60。結果は 58 件（2 件は範囲外）。Chromium の 8 件は今も非公開で、NVD の部品名だけで分けた。COOP・COEP・CORP・SAB・opener の語では、ブラウザの欠陥は 1 件も出なかった（NVD は site isolation や Navigation として登録する）。

- 1 件ごとに新しい変異体になるものは無かったので、型から作った。多いのは欠落（検査の欠落、古い値）で、作者の変異体はほとんど条件の反転（neg:）だった。そこで、欠落の形の変異体を 66 個作った（すべての判断の true: と false:、リダイレクトの 6 形）。

**殺し方**（前と同じ規則、Chrome 158 と Firefox 160 の観測）

- 等価のうち 1 つ（cors のモードの取得の検査を落とす）は本物の穴で、どの観測の集合にも、別オリジンの cors のモードの取得の行が無い。

**欠けた軸**（バグの数の順）

1. レンダラーへの信頼と IPC（8）。
2. UI と利用者の操作（7）、Web の外の面（7）。
3. 今の軸にあるがモデルに無い段（15）: sandbox の旗（5）、リダイレクトで運ばれる COOP 以外の値（Origin の汚れ、referrer policy、CSP の報告の URL）（4）、履歴の項目（2）、document.domain のオリジンの領域の検査と Window の再利用（2）、worker の方策の容れ物（1）、ORB（1）。
4. プロセスのモデル（3）、キャッシュと bfcache（3）、サイドチャネル（3）、競合と寿命（2）。

読み取れること:

- R1（殺す）は、書けるものについて当たった。バグから作った変異体も、作者の変異体と同じ率で殺された。
- R2（多くは軸の外）が当たった。58 件のうち 51 件（88%）が、観測の試す範囲の外にある。
- R3（変異体に写せない）が一部当たった。57% は実装の構造の誤りで、モデルの段の言葉で書けない。
- 作者の変異体（条件の反転）とバグの型（欠落）は、形がずれていた。形を合わせても殺す率は変わらず、問題は形ではなく軸だった。

## 結果を攻撃する

経緯を知らない subagent 2 体（形式手法、ブラウザの実装と仕様の編集）に、A2・C4・A1・C9・B2a と B2d・D2 の結論をまとめて攻撃させた（ユーザーの判断: 作業の木の高・中がなくなるまで）。形式手法の観点は記憶で論じ、ブラウザの観点は仕様の本文と PR を 2026-11-24 に確かめた。筆者は、モデルの性質が CHOOSE と Cardinality を使わないこと（CHOOSE は反例の証人の定義だけ）と、compose/ の契約に liveness が無いことを確かめた。

## 結論

公開で直った欠陥 58 件から型を作ると、モデルの段で書ける型の変異体は、作者の変異体と同じ率でこれまでの観測に殺された。しかし欠陥の 88% は観測の軸の外（レンダラーへの信頼、UI、Web の外の面、プロセス、キャッシュ、競合）にあり、殺す率が覆うのは実際の欠陥の約 12% にとどまる。欠落の形の変異体は、形はバグの型から決めたが当てる場所は汎用で、個々の欠陥を作り直した変異体は 7 件（すべて殺された）だけ。集め方は NVD の語の検索に偏る。モデルの段で書けるのに欠けた軸は作業の木の C11 に、モデルの外の型は C5 に入れた。

生き残った選択肢: R1（書けるものについて）と R2。

## 次の問い

- 個々の欠陥の誤った条件を、モデルの段の変異体として作り直す（7 件より多く）。軸の外の欠陥の型のうち、モデルを広げれば書けるものはどれか。

## 経過

- 2026-11-24 段階A。問いと対立仮説を置いた。
- 2026-11-24 段階B。公開で直った 58 件の欠陥から型を作り、欠落の形の変異体 66 個を作った。殺す率は作者の変異体と同じだったが、欠陥の 88% は観測の軸の外にあった。欠けた軸を数の順に並べた。
- 2026-11-24 段階C。攻撃を受けて、殺す率が覆うのは実際の欠陥の約 12% と書き、変異体の作り方の名ばかりの部分と集め方の偏りを限界に書いた。結論を出した。
