# 段の中の条件の意味を決めれば、性質に効く値を書く段の一覧を閉じられるか

- 更新: 2026-11-24

- 木の節: browser-semantics-soundness/B2b、browser-semantics-soundness/B2c

## 問い

置き換えの思考実験では、書き先の 57% が規則で決まらず（Let の局所変数、集まりの操作）、写していない段の一覧が閉じなかった。局所変数を、それが最後にどこへ流れるか（返り値、構造体の欄、他の算法の引数）でたどる、段の中のデータの流れの解析を作れば、性質が読む値に流れ込む段の一覧を閉じられるか。閉じた一覧と、モデルが写した段を突き合わせると、写していない段のうち性質に効くものはいくつ残るか。

問いの出し方（ユーザーの判断）: 作業の木の効きが高・中の節がなくなるまで進める（/goal）。Claude は、互いにぶつからない作業の束に分けて並行で進め、この記録はその束の 1 つ。

## 前提

- 取り出した段の表（closure_steps.tsv）と、havoc/writesets.tsv を使う。
- 「閉じる」は、性質が読む値ごとに、そこへ流れ込みうる段がすべて一覧にある、という意味。解析が扱えない段は穴として数え、穴が 0 でなければ閉じていない。
- モード: 構成的。

対立仮説:

- R1 閉じる。局所変数の流れをたどれば、書き先はほぼ決まる。
- R2 閉じない。条件の文（自然言語）や、他の仕様への受け渡しで、流れが途切れる。
- R3 閉じるが、写していない段で性質に効くものが多く残り、モデルの網羅は思ったより低い。

設定の欠陥: 解析は散文の段を形の規則で読むので、意味の取り違えは測れない。

## 条件を変える

**操作 1（1 巡目）: 段の中のデータの流れの解析**

subagent が、HTML と Fetch の原稿の段（全体で 10,198、閉包の中で 3,445）を、変数・欄・引数・返り値の定義と使用に分け、算法の中と呼び出しをまたいだデータの流れを作り、性質が読む 13 の概念（24 の置き場所）へ流れ込む段を逆にたどった（[dataflow/](models/site-isolation/dataflow/RESULTS.md)、flows.tsv、closed-list.tsv、holes.tsv）。筆者は報告を読んだ。

- 合わせて 87.7% の書き先が規則で決まった。残りは 117（変数でない書き先の Let 45、集まりの操作 48、読めない 24）。
- 性質に流れ込む段（データと制御の依存）は 2,218 で、そのうちモデルが写したのは 120、写していないのは 1,727。概念ごとの集合がどれもほぼ同じ大きさ（2,217〜2,218）で、関係は飽和した。オブジェクトも呼び出しの文脈も区別しない解析の結果で、このままでは一覧が判別の力を持たない。性質の値から 2 段以内の写していない段は 572（ナビゲーションと履歴 148、リダイレクトとネットワーク 132、文書の作成 90 など）。
- 既知の 2 つの欠落（obtain an embedder policy の 2 段目、HTTP-network-or-cache fetch の 8.4 段）は、手の種なしで、どちらもデータと制御の集合に入った（距離 0 と 2）。データだけの集合には入らず、制御の依存が要った。
- 性質に関わる経路の上の穴: 144 段（書き先の決まらない集まりの操作 35、間接の呼び出し（processResponse のような callback）34、散文だけの段 28、書き先の無い集まりの操作 21、ほか）と、束縛されない局所変数 48（散文で定義した算法の引数、callback の引数、印の無い繰り返しの変数）。他の仕様の算法の呼び出し 401 段は、引数だけの関数とみなした（仮定で、穴とは数えていない）。

読み取れること（1 巡目）:

- R1（閉じる）は当たらなかった。書き先の多くは決まるが、穴は 0 でない。
- R2（流れが途切れる）が当たったが、自然言語の条件のせいではなかった。条件は制御の依存に効くだけで、その語で足りる。途切れるのは受け渡し（callback、書き先の無い集まりの操作、散文だけの段、他の仕様の呼び出し）。
- R3（写していない段が多く残る）が、但し書きつきで当たった。数の一部は、オブジェクトも文脈も区別しない解析の作り。

2 巡目で、callback の束縛、残った集まりの操作の書き先、他の仕様の呼び出しの扱い（入力として宣言する）、オブジェクトを区別する解析を足す。

**操作 2（2 巡目）: 受け渡しを束縛し、契約を明示する**（[dataflow/round2/](models/site-isolation/dataflow/round2/RESULTS2.md)、contracts.py、inputs.tsv、residual-targets.tsv）

- callback: 「次の段を X とし、…を与える」などの形から登録し、引数として渡された callback も呼び先の引数の名で登録した。閉包の間接の呼び出し 77 のうち、束縛 19、値を渡さないもの 17、引数の無い callback 1、型ごとのフック 15（契約 C4）、WebDriver BiDi のフック 25（C3）、束縛できないもの 0。間接の呼び出しの穴は 34 → 0。束縛されない局所変数は 48 → 10 で、10 はどれもモデルが読む概念を書かない（散文の関数、存在の束縛など）。
- 書き先: Let の局所変数 746/746、集まりの操作 141/152、読めない 47/56。合わせて 954 行のうち 934（97.9%）が規則で決まり、残る 20 はどれも契約で説明される（URL の username と password の setter と Streams と Fetch Metadata は C1、JS の実行文脈とイベントループと積まれたタスクと DOM の木は C5、HTTP キャッシュは C6）。
- 他の仕様の呼び出し: 1 巡目の 401 のうち 414 の参照は呼び出しではなく項（型、述語、定数）。残る呼び出しは 73 の算法、103 の段で、inputs.tsv に入力の契約として書いた（純粋 C1 60、script を走らせる C2 5、BiDi C3 6、ほか）。どれもモデルが読む概念を書かない（BiDi のネットワークの横取りは C3 で、script は C2 で外した）。上位 20 のうち 3 は url.bs と照らして確かめ、17 は記憶。
- 散文だけの段: 制御の経路の上の 19 のうち、値を書かないもの 6、書くがモデルが読む概念ではないもの 13。
- 判別の力: 1 つの呼び出しの場所の文脈と、割り当ての場所の heap（300 の場所）を足しても、データと制御の集合は概念ごとに 2,275〜2,276 で飽和したまま。原因は、取得の道筋の request が、仕様の 97 の割り当ての場所すべてを指すこと。データだけの集合は、CORP・資格情報・mode・tainting・安全・cross-origin isolated・グループの切り替え・COOP で 5〜20 段、COEP・オリジン・応答・COI の mode・エージェントクラスタの鍵で 924〜941 段。
- 既知の 2 つの欠落は、すべての集合に入ったまま。

**一覧**: 契約 C1〜C7 のもとで、性質に関わる経路の上の穴は 0（「モデルが読む概念を書きうるか: 不明」の段が残らない）。性質に効く写していない段（データと制御）は 1,864（置き換えで書き先が決まらなかったもの 721、書き込みでないもの 1,096、既知 47）、うち性質の値から 2 段以内が 641。群は、URL と解析 558、ナビゲーションと履歴 464、リダイレクトとネットワーク 273、文書と閲覧の文脈の作成 176、script とイベント 100、取得の核 88、方策 75、ほか 130。データだけの一覧は 696 段。一覧は、効く段を漏らさない上位集合で、効く順の順位ではない。

読み取れること（2 巡目まで）:

- R1（閉じる）は、契約を明示したもとで当たった。書き先の 97.9% が規則で決まり、残りは契約で説明でき、穴は 0。
- R2（流れが途切れる）は、途切れ目を契約として名づけることで扱えた。途切れ目は自然言語の条件ではなく、受け渡しと他の仕様だった。
- R3（写していない段が多く残る）が当たった。モデルが写したのは約 120 段で、性質に関わる段（約 2,300）のごく一部。一覧は、モデルの網羅の低さを数で示すが、関わる段が飽和するので、どの段が効くかの順位は付けられない（判別には、深さ 4 以上の呼び出しの文脈か、モデルが量化する入力で切ることが要る）。
