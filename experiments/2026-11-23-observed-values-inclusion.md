# ブラウザが実際に返した値はすべてモデルが許す値か（実装 ⊆ モデル）

## 問い

モデルでの安全性の証明がブラウザに移るのは、ブラウザのすべての振る舞いがモデルの振る舞いであるとき（実装 ⊆ モデル）。これまでの WPT との照合は、モデルを試験の作者の期待値と比べたもので、ブラウザが実際に返した値とは比べていない。WPT の 109 件の筋書きで、Chrome と Firefox が実際に返す値を記録し、その値がすべて、モデル（非決定とパラメータを含む）の許す値の集合に入るかを確かめる。入らない値があれば、その値の分だけ、モデルの証明はそのブラウザに移らない。

問いの出し方（ユーザーの判断）: 先行研究を調べたあと、価値の高い順の 1 位（この問い）と 2 位（havoc）を並行で進める。先行研究では、ブラウザについてこの向きを確かめたものは見つからなかった（調査の報告者の推論）。手本は、メモリモデルをハードウェアの観測で確かめる litmus と herd の型。

## 前提

- 観測: 各試験の筋書きを、合否ではなく、試験が比べている値そのもの（crossOriginIsolated、originAgentCluster、取得の結果が basic・opaque・誤りのどれか、popup の opener が切れたか など）を記録する形に写す。
- モデルが許す値の集合: WPTBroad.tla の各試験の筋書きについて、モデルの出力を、非決定とパラメータ（cross-origin isolation mode の "logical" と "concrete" など）をすべて動かして集める。
- 包含の判定: 観測した値が集合に入るか。入らない値は「モデルの外の振る舞い」として数え、原因を、モデルの欠落・ブラウザの欠陥・観測の写し方の誤りに分ける（どれかは手で判定し、判定は 1 人）。
- 対照（判別の力を測る）: わざと誤ったモデル（既存の誤読の包みの変異体）で同じ判定をすると、包含が崩れる観測が出なければならない。どの変異体でも包含が崩れないなら、観測がモデルの違いを見分けておらず、包含が成り立っても空。
- 安全の配慮: 包含が崩れた値がブラウザの欠陥で、まだ公開されていないものに当たる場合は、詳細を記録の外に置き、扱いをユーザーに確かめる（前の 2 件と同じ）。
- モード: 構成的（確かめる手順を作り、動かす）。採らなかった候補は、破壊的。

対立仮説:

- R1 包含は成り立つ。Chrome と Firefox の値は、WPT で失敗する試験を含めて、モデルが許す値に入る（失敗はブラウザが仕様の別の選択肢を取っているだけ）。
- R2 包含は崩れる。ブラウザはモデルが許さない値を返す試験がある。そこでは、モデルの証明はそのブラウザに移らない。
- R3 写し方が律速になる。観測をモデルの出力に写すこと（実装の状態とモデルの変数の対応づけ）が、試験ごとに手作業になり、断片をまたいで流用できない（トレースの検証で報告された難しさ）。
- R4 包含は空になる。モデルの出力が粗く（取得の結果が 3 値など）、どの変異体でも包含が崩れない。包含は成り立つが、何も示さない。

設定の欠陥: 観測するのは WPT の筋書きの入力だけで、筋書きに無い入力でのブラウザの振る舞いは測れない（試した範囲だけ）。観測は 1 つのエンジンの 1 つの版で、版や構成によって変わりうる。
