# ブラウザが実際に返した値はすべてモデルが許す値か（実装 ⊆ モデル）

## 問い

モデルでの安全性の証明がブラウザに移るのは、ブラウザのすべての振る舞いがモデルの振る舞いであるとき（実装 ⊆ モデル）。これまでの WPT との照合は、モデルを試験の作者の期待値と比べたもので、ブラウザが実際に返した値とは比べていない。WPT の 109 件の筋書きで、Chrome と Firefox が実際に返す値を記録し、その値がすべて、モデル（非決定とパラメータを含む）の許す値の集合に入るかを確かめる。入らない値があれば、その値の分だけ、モデルの証明はそのブラウザに移らない。

問いの出し方（ユーザーの判断）: 先行研究を調べたあと、価値の高い順の 1 位（この問い）と 2 位（havoc）を並行で進める。先行研究では、ブラウザについてこの向きを確かめたものは見つからなかった（調査の報告者の推論）。手本は、メモリモデルをハードウェアの観測で確かめる litmus と herd の型。

## 前提

- 観測: 各試験の筋書きを、合否ではなく、試験が比べている値そのもの（crossOriginIsolated、originAgentCluster、取得の結果が basic・opaque・誤りのどれか、popup の opener が切れたか など）を記録する形に写す。
- モデルが許す値の集合: WPTBroad.tla の各試験の筋書きについて、モデルの出力を、非決定とパラメータ（cross-origin isolation mode の "logical" と "concrete" など）をすべて動かして集める。
- 包含の判定: 観測した値が集合に入るか。入らない値は「モデルの外の振る舞い」として数え、原因を、モデルの欠落・ブラウザの欠陥・観測の写し方の誤りに分ける（どれかは手で判定し、判定は 1 人）。
- 対照（判別の力を測る）: わざと誤ったモデル（既存の誤読の包みの変異体）で同じ判定をすると、包含が崩れる観測が出なければならない。どの変異体でも包含が崩れないなら、観測がモデルの違いを見分けておらず、包含が成り立っても空。
- 安全の配慮: 包含が崩れた値がブラウザの欠陥で、まだ公開されていないものに当たる場合は、詳細を記録の外に置き、扱いをユーザーに確かめる（前の 2 件と同じ）。
- モード: 構成的（確かめる手順を作り、動かす）。採らなかった候補は、破壊的。

対立仮説:

- R1 包含は成り立つ。Chrome と Firefox の値は、WPT で失敗する試験を含めて、モデルが許す値に入る（失敗はブラウザが仕様の別の選択肢を取っているだけ）。
- R2 包含は崩れる。ブラウザはモデルが許さない値を返す試験がある。そこでは、モデルの証明はそのブラウザに移らない。
- R3 写し方が律速になる。観測をモデルの出力に写すこと（実装の状態とモデルの変数の対応づけ）が、試験ごとに手作業になり、断片をまたいで流用できない（トレースの検証で報告された難しさ）。
- R4 包含は空になる。モデルの出力が粗く（取得の結果が 3 値など）、どの変異体でも包含が崩れない。包含は成り立つが、何も示さない。

設定の欠陥: 観測するのは WPT の筋書きの入力だけで、筋書きに無い入力でのブラウザの振る舞いは測れない（試した範囲だけ）。観測は 1 つのエンジンの 1 つの版で、版や構成によって変わりうる。

## 条件を変える

固定: SpecIsolation.tla（2 段を足した版）と WPT の 109 件の筋書き。変える: 比べる相手（試験の期待値か、ブラウザが実際に返した値か）と、モデルの変異体。

subagent が観測の試験を書き、podman の中で Chrome 158.0.8127.36 と Firefox 160.0.1 に 2 回ずつ動かし、モデルが許す値の集合を TLC で求めて比べた（[observe/](models/site-isolation/observe/RESULTS.md)。WPT のクローンは 31362d122）。筆者は報告を読んだ。

**写す手間**: 109 件すべてを写せた（写せなかった行は 0）。試験のファイル 11 個と補助 2 個で済み、各観測を「OBS <行> :: <値>」という通る小試験として出した。入力は元の試験の URL、ヘッダー、モード、順序のまま。Origin-Agent-Cluster の筋書きは、新しいブラウジングコンテキストグループにするため noopener の popup で動かした。2 回の繰り返しで、すべての行の値が同じだった。元の試験を手元で動かした合否も、下の分類と合った。

**包含**（変異の無いモデル、cross-origin isolation mode は concrete と logical の両方を許す）

- Firefox は 109 件中 108 件、Chrome は 92 件で、観測した値がモデルの許す値に入った。
- Chrome は、ヘッダーが無くても、グループの過去の鍵がサイトでも、安全な文脈の窓をオリジンで区切る（http では偽）。外れ方は隔離を厳しくする側で、wpt.fyi で既に失敗として公開されている。伏せるものは無かった。
- HTML の本文では、エージェントクラスタと popup の COOP の段に実装の選択は無く、cross-origin isolation mode がモデルの唯一のパラメータだった。

**判別の力**（変異体 43 個: neg の 27 と、名前つきの 16）。変異の無いモデルの集合に入り、変異体の集合に入らない観測があれば、その変異体を殺したと数えた（モデルの外の観測で殺したことにしないため）。

| cross-origin isolation mode | 殺した | この行では等価 | 違うが生き残った |
| --- | --- | --- | --- |
| concrete と logical | 38 | 3 | 2 |

- Chrome と Firefox は同じ変異体の集合を殺した。殺した集合は、試験の期待値を観測として入れたときと同じだった。観測した値は、期待値を超える判別の力を足さなかった。
- 両方のブラウザが、logical なら外れる 6 行で真を返したので、両方とも concrete を選んでいる（前の思考実験と一致）。
- 等価な 3 個は、cl-ignore-creds、crossorigin-as-site、neg:coep-cl-strips。credentialless の資格情報を落とす段の欠落は、観測でも見分けられない（前の記録で WPT が捕まえなかったのと同じ）。

読み取れること:

- R1（包含は成り立つ）は、Firefox と、Chrome の取得・popup・cross-origin isolated の部分で当たった。そこでは、試した 109 点でモデルの証明がブラウザに移ることを支える（詳細化の証明ではなく、点の上の支え）。
- R2（包含は崩れる）は、Chrome の Origin-Agent-Cluster と document.domain で当たった。ここでは、モデルの結論は Chrome に移らない。Chrome を確かめるには「安全な文脈ではいつもオリジンで区切る」というパラメータがモデルに要る。両方のブラウザで、Mixed Content の欠落も外れを生んだ。
- R3（写し方が律速）は当たらなかった。この断片では、写す手間は試験のファイル 11 個で済んだ。
- R4（包含は空）は当たらなかった。変異体の 38〜40 個を殺した。ただし、殺せる変異体は期待値と同じで、観測の価値は「期待値とブラウザが食い違う所を、モデルの外の値として特定すること」にあった。

## 結果を攻撃する

経緯を知らない subagent 2 体（形式手法、ブラウザの実装と試験の基盤）に、この思考実験と havoc の思考実験の結論を合わせて攻撃させ、並行して、見つかった欠落をモデルに直して確かめ直した（ユーザーの判断: 1 と 2 を並行）。形式手法の観点は記憶で論じ、ブラウザの観点は whatwg/html の PR などを確かめた。筆者は、モデルが許す値の集合の大きさを測った: 109 行のうち 103 行で 1 値、6 行で 2 値（cross-origin isolation mode の 2 つ）。

- w014 の原因が分かった。Mixed Content が画像を https に上げ、ポートは 8000 のまま。WPT のサーバーの 8000 番は平文の HTTP なので、TLS の要求が 400 になる。モデルの欠落でもブラウザの欠陥でもなく、試験の作りの結果だった（ポートはログの時刻からの推測）。
- 直したことで、性質の書き方が分かれた。前提を上の段だけにした OptInOnlySecure は構造上変わらず、すべての文脈に広げた版は偽（http の最上位の下の https）、安全な文脈で書いた版と方策の容れ物の COEP で書いた版は真。
- 副作用: DIPExtension.tla と havoc/HavocSpec.tla の「変わらない」の検査が偽になった（それぞれの取得の写しに Mixed Content が無いため。HavocSpec は false:mc-block で真に戻る）。observe/RESULTS.md は直す前のモデルについての記述。

## 結論

ブラウザが実際に返した値をモデルの許す値と比べる方法は、写す手間が小さく（109 行をファイル 11 個で）、空でもない（集合は 1〜2 値）。ただし、示すのは「モデルの段の関数が、1 回きりの筋書きの 109 点でブラウザと一致する」ことまでで、モデルの安全性の証明がブラウザに移る根拠にはならない。証明は入力と状態の列のすべてを量化するが、筋書きは 1 回きりで、入れ子の枠も、リダイレクトも、履歴の移動も含まない。観測は、変異体を期待値以上には見分けず、価値は、モデルの仕様の時点とブラウザが食い違う所を特定することにあった（Chrome の 16 行は未統合の HTML の変更 #7617、w014 は試験の作り）。見つかった欠落を直しても、この方法には入れ子の枠の修正が見えなかった。

前提:

1. 経験的（ブラウザ、2 回の繰り返し）: Firefox 160 は 109 中 108、Chrome 158 は 92 が内側。
2. 経験的（TLC）: 集合は 103 行で 1 値、6 行で 2 値。変異体 43 個中 40 個を殺し、殺した集合は期待値と同じ。
3. 確認した事実（subagent が確かめた）: whatwg/html#7617 は未統合で、Chromium は M115 で出荷した。
4. 経験的（直したモデル）: 包含と期待値の照合は、Mixed Content の修正だけを見た。
5. 未検証: noopener の popup による写し方、プロセスの水準の隔離。

生き残った選択肢: 「1 回きりの点での適合の証拠で、食い違いの場所を特定する道具」。脱落: 「109 点でモデルの証明がブラウザに移ることを支える」、「Chrome の 16 行はブラウザの食い違い」、R4（空）。

## 次の問い

- 筋書きを構造の軸（入れ子の深さ、リダイレクトの段数、履歴の移動、popup の系譜）に沿って機械的に作れるか（メモリモデルの litmus の試験を軸に沿って作る diy の型）。作った筋書きで、入れ子の枠の修正が見えるようになるか。
- モデルを #7617 の後の既定に合わせると、Chrome の 16 行が内側に入り、Firefox の対応する行が外に出るか（仕様の時点を変えたときの包含）。

## 経過

- 2026-11-23 段階A。問いと対立仮説 R1〜R4、判別の力の対照を置いた。
- 2026-11-23 段階B。Firefox は 109 件中 108 件、Chrome は 92 件で、観測した値がモデルの許す値に入った。外れは、Chrome の Origin-Agent-Cluster の既知の食い違い（16 行）と、Mixed Content の欠落（1 行、両方）。写す手間は小さく、変異体の 40 個を殺したが、期待値を超える判別の力は無かった。
- 2026-11-23 段階C（ユーザーの判断: 1 と 2 を並行）。新しい subagent 2 体の攻撃で、主張を「1 回きりの点での段の関数の一致」に弱め、Chrome の 16 行を未統合の HTML の変更（#7617）に改めた。直したモデルでも、この方法には入れ子の枠の修正が見えなかった。結論を出した。
