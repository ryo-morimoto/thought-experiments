# 拡張に耐える条件（支配の条件と漏らす一覧）は、手書きのモデルで確かめられるか

- 状態: 結論済み
- 開始: 2026-11-21
- 更新: 2026-11-22
- 関連: [experiments/2026-11-21-informal-extension.md](2026-11-21-informal-extension.md)（この記録の前提を出した思考実験）、[maps/browser-semantics-soundness/map.toml](../maps/browser-semantics-soundness/map.toml) のセル「非形式 × 拡張」、[ExtensionHooks.tla](models/site-isolation/ExtensionHooks.tla)
- 木の節: browser-semantics-soundness/B4、browser-semantics-soundness/B5

## 問い

「非形式 × 拡張」の結論は、2 つの未検証の前提に依っていた。

1. 支配の条件: 別オリジンの中身を届けるすべての経路が、拡張に迂回されない基の検査を通る。これが成り立てば、止めるだけの差し込みはアクセス制御を保つ。
2. 漏らす一覧: 情報流の性質には、意図して漏らすもの（基の Fetch の ORB が本文を嗅いで止めるかを決める、など）の明示した一覧が要る。

この 2 つを、手で書いたモデルで確かめられるか。確かめたとき、結論はどう変わるか。

問いの出し方（ユーザーの判断）: 前の思考実験の「次の一手」の 1 と 2 を並行で進める。

## 前提

- モデルは SpecIsolation.tla（2 段を足した版）と ExtensionHooks.tla。既存のファイルは変えず、新しいモジュールで足す。
- 「支配の条件」の反例の候補は、止められたあとに別の経路で取り直すこと（img の onerror から iframe のナビゲーションで取り直す、object の代替の中身、再試行）。
- モード: 構成的（条件をモデルで確かめる）。採らなかった候補は、破壊的（条件が崩れる例だけを探す）。

対立仮説:

- R1 支配の条件は、今の HTML・Fetch で成り立つ。取り直しの経路（ナビゲーション）にも CORP と COEP の検査がある。
- R2 支配の条件は成り立たない。止められたことで開く経路が、基の検査を通らずに中身を届ける。
- R3 漏らす一覧は短く書ける（ORB が漏らすのは、止めたか否かの 1 ビットと、その判断に使う型の情報だけ）。
- R4 漏らす一覧を足すと、情報流の性質はほとんど何も言わなくなる（本文の嗅ぎ分けが中身の多くを漏らす）。

設定の欠陥: モデルが写す経路は、写した分だけ。支配の条件が「写した経路で成り立つ」ことは、写していない経路（キャッシュ、service worker、prefetch）について何も言わない。

## 条件を変える

固定: SpecIsolation.tla（2 段を足した版、`Mutant = "none"`）。変える: 取り直しの経路と、基の検査の置き場所（ユーザーの判断: 1 と 2 を並行）。

**操作 1: 支配の条件**

Fetch の「HTTP fetch」は、CORP の検査を HTTP-network-or-cache fetch が返した応答に対して行う（fetch.bs d7fc0fd、5895〜5905 行付近）。HTTP-network-or-cache fetch の中には、認証のあとの取り直しやキャッシュが入るので、検査はそのあとに来る。[DominanceRetry.tla](models/site-isolation/DominanceRetry.tla) で、内部の取り直しのある no-cors の取得と、止められたあとにページが iframe のナビゲーションで取り直す経路を写し、検査の置き場所を変えた（[Dominance-after.cfg](models/site-isolation/Dominance-after.cfg)、[Dominance-before.cfg](models/site-isolation/Dominance-before.cfg)）。差し込みは止めるだけで、何を読んでもよい。

<!-- data-source: original（筆者のモデルを TLC で検査した結果） -->
| 検査の置き場所 | 取り直しのある取得 | 止められたあとのナビゲーション |
| --- | --- | --- |
| 取り直しのあと（仕様） | 成り立つ | 成り立つ |
| 最初の応答だけ（仮の仕様） | 成り立たない | 成り立つ |

反例（仮の仕様）: 最初の応答は CORP same-site（同意あり）、資格情報つきの取り直しへの応答は CORP なし。最初の応答だけを確かめると、同意の無い応答の中身が届く。

読み取れること:

- 写した経路では、支配の条件は仕様の段の置き場所から出る。検査が取り直しのあとの最後の応答に掛かるので、止めるだけの差し込みがどこで止めても、届く中身は基の検査を通る。
- ページが止められたあとに別の経路（ナビゲーション）で取り直しても、その経路にも基の検査（forNavigation の CORP の検査と、子の COEP）がある。ページが自分で選べる経路は、差し込みが無くても選べるので、止めることで新しく開く経路ではない。
- 支配の条件で効くのは、差し込みの性質ではなく、基の仕様の検査の置き場所だった。崩れるとしたら、取得を通らずに中身を使う経路。写していない候補は、取得を通らずに応答を再利用する経路（段階C で見直した）。

**操作 2: 漏らす一覧（ORB）**

subagent がモデルを書いて動かし、筆者は報告と [ORB-NOTES.md](models/site-isolation/ORB-NOTES.md) を読んだ（[ORBExtension.tla](models/site-isolation/ORBExtension.tla)、[ORB.cfg](models/site-isolation/ORB.cfg)）。

まず、ORB は Fetch の d7fc0fd に入っていなかった（fetch.bs に ORB の本文は無く、近いのは script 系の行き先だけの「MIME の型による阻止」、nosniff、範囲の状態の検査）。ORB は取り込まれていない Fetch の PR #1442 にある。したがって、前の思考実験の形式手法の反論「基の Fetch にある ORB が本文を嗅ぐ」は記憶の誤りで、前の結論の範囲の分け方では、ORB は取り込まれた本文ではなく拡張になる。モデルは PR #1442 の ORB の算法を写した（PR では CORP の検査の前に置かれ、止めればネットワークの誤り）。

ORB は、MIME の型の分類、nosniff、状態、メディアの要求の状態、最初の 1024 バイトの嗅ぎ分け、本文全体が JavaScript として読めて JSON でないか、を読む。後の 2 つは本文の関数。

<!-- data-source: original（subagent のモデルを TLC で検査した結果の集計） -->
| 宣言に足したもの | NoUndeclaredLeak |
| --- | --- |
| 何も足さない | 成り立たない（本文が音声・動画と嗅がれれば誤り、画像なら不透明。JS なら不透明、JSON なら誤り） |
| 応答の MIME の型・nosniff・状態 | 成り立たない（同じ反例） |
| 上に、嗅ぎ分けの分類だけ | 成り立たない（JS と JSON） |
| 上に、JS として読めるかだけ | 成り立たない（音声・動画と画像） |
| 上に、嗅ぎ分けの分類と JS として読めるか | 成り立つ |
| ORB の判定の 1 ビットだけ | 成り立つ（最小） |

ORB を入れても、OptInOnlySecure と BodyOnlyByOptIn は成り立ち、ORB は止める側を足すだけだった。

漏らす一覧:

- 相手が宣言したもの: MIME の型、nosniff、状態。説明には要るが、それだけでは足りない。
- 本当に意図して漏らすもの: 本文の段に入ったあとの ORB の判定。本文の 2 つの述語の関数。
- 量: 要求ごとに 1 ビット。ページがメディアの要求の状態を変えて取り直せば、1 つの応答について本文は高々 3 つの類（画像か JS、音声・動画、その他）に分かれ、高々 log2 3 ≒ 1.58 ビット。秘密の値そのものは、この抽象では流れない。
- 写していないもの: 時間と大きさ（本文全体を読む段は大きさを漏らしうると、ORB の説明文書が書く）、部分応答の検査、本文の読み取りの失敗、攻撃者が中身を混ぜ込める本文（JS として読めるかが秘密の判定器になる）。

**2 つの操作を合わせて**

- 支配の条件（操作 1）は、写した経路では基の Fetch の検査の置き場所から出た（R1）。止めるだけの差し込みは、何を読んでもアクセス制御を保つ。崩れうるのは取得を通らない経路で、まだ写していない。
- 漏らす一覧（操作 2）は短く書けた（R3）。ORB の判定の 1 ビットを宣言に足せば、情報流の性質は戻る。性質がほとんど何も言わなくなる（R4）ことは、この抽象では起きなかった。ただし時間と大きさを入れれば一覧は伸びる。
- 前の思考実験の結論のうち「情報流には漏らす一覧が要る」は、ORB を拡張として閉包に入れたときに要る、と言い直す。取り込まれた本文の Fetch だけなら、ORB による本文の嗅ぎ分けは無い。

## 結果を攻撃する

経緯を知らない subagent 2 体（形式手法、ブラウザの実装）に段階B の結論を攻撃させ、並行して、取得を通らずに応答を再利用する経路を仕様の本文とモデルで確かめた（ユーザーの判断: 1 と 2 を並行）。

**再利用の経路の確認**（subagent が仕様の本文を読み、モデルを書いて動かした。筆者は報告を読んだ）: 内部の取り直しとは別に、応答を取得し直さずに使う経路を 7 つ見た（Prefetch の草案は 2026-11-21 に取得、sha256 f671cd51…706de3）。5 つでは支配の条件が成り立った。2 つでは、仕様の本文が支配の条件を保証しなかった。実際のブラウザの振る舞いは確かめていない。この 2 つの経路と、どう崩れるかの詳細は、確かめるまで記録・地図・モデルから外した（ユーザーの判断。リポジトリが公開であるため）。成り立った経路で効いていたのは、再利用の鍵に文書が入っていること、または検査が使うたびに掛かることだった。

## 結論

このセルの前提についての結論: 2 つの条件はどちらも、仕様の構造から読み取れるものではなく、手書きのモデルでは「確かめた経路について成り立つか」までしか言えない。

- 支配の条件は、基の仕様の性質で、別オリジンの中身が文書に入る経路（取得、取り直し、ナビゲーション、取得を通らない再利用）ごとに確かめる必要がある。確かめた範囲では、取得の中の取り直しと 5 つの再利用の経路で成り立ち、2 つの再利用の経路で仕様の本文が保証しなかった（詳細は外した）。したがって、取り込まれた本文に範囲を限っても、アクセス制御の結論は、写した経路についての結論にとどまる。
- 漏らす一覧は、項目ごとに「攻撃者が選べない、秘密の固定した関数」でなければ意味を持たない。ORB の判定は、攻撃者が本文に中身を混ぜ込めれば攻撃者が選ぶ述語になるので、宣言に足しても漏れを定義で消すだけになる。確かめるには、攻撃者が入力を選び、問い合わせを繰り返す形の検査（自己合成、k 回の問い合わせの hyperproperty）が要る。モデルは漏れを見つけられるが、一覧が尽きていることは示せない。

前提:

1. 経験的（TLC）: 取り直しのあとに検査を置く仕様では成り立ち、最初の応答だけでは崩れる（DominanceRetry.tla）。ORB を入れると情報流が崩れ、判定の 1 ビットを宣言に足すと戻る（ORBExtension.tla）。
2. 経験的（仕様の本文とモデル、1 体の subagent）: 再利用の 7 つの経路のうち 2 つで、本文が支配の条件を保証しない。エンジンでは確かめていない。
3. 確認した事実（subagent が出典を確かめた）: ORB は Fetch の PR #1442（未統合）にあり、Chrome と Firefox で出荷され、振る舞いが違う。
4. 未検証: リダイレクト、状態を持つ差し込み、攻撃者が中身を混ぜ込める本文での ORB の漏れの量、時間と大きさ。

生き残った選択肢: R2 を経路ごとに言い直したもの（基の仕様に、検査を通らない経路がある。差し込みが開くのではなく、基の仕様にもとからある）。脱落: R1（支配の条件は今の HTML・Fetch で成り立つ）、段階B の「支配の条件は検査の置き場所から出る」、R3（漏らす一覧は短く書ける）。R4（性質がほとんど何も言わなくなる）は、攻撃者が中身を混ぜ込める本文では当たりうるが、確かめていない。

## 次の問い

- 本文が支配の条件を保証しなかった 2 つの経路を、実際のエンジンで確かめる（結果を見てから、公開と上流への報告を決める。詳細は記録の外に置いた）。
- 攻撃者が中身を混ぜ込める本文で、ORB の判定から何ビット読めるかを、k 回の問い合わせの自己合成で数える。
- 別オリジンの中身が文書に入る経路の一覧を、仕様の本文から機械的に作れるか（取得の呼び出しと、取得を飛ばす再利用の箇所）。

## 経過

- 2026-11-21 段階A。前の思考実験の 2 つの未検証の前提を問いにし、対立仮説 R1〜R4 を置いた。
- 2026-11-21 段階B の操作 1。CORP の検査は取り直しのあとの最後の応答に掛かるので、写した経路では支配の条件が成り立った。最初の応答だけを確かめる仮の仕様では崩れた。効くのは基の検査の置き場所。
- 2026-11-21 段階B の操作 2。ORB は Fetch の d7fc0fd に無く、PR #1442 にある拡張だった。ORB を入れると情報流は崩れ、判定の 1 ビット（応答あたり高々 1.58 ビット）を宣言に足せば戻った。漏らす一覧は短く書けた。
- 2026-11-22 段階C（ユーザーの判断: 1 と 2 を並行）。再利用の経路を確かめ、2 つで仕様の本文が支配の条件を保証しなかった（詳細は外した、ユーザーの判断）。新しい subagent 2 体の攻撃で、R1 と「検査の置き場所から出る」と R3 を取り下げた。結論を出した。
