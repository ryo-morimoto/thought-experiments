## 問い

tellman-naming を4回呼んで、ようやく指摘が出なくなった。1回の呼び出しで同じところに届かせるには、直前に挙げた5点の局所修正（削除・統合を判定表に入れる、名前を全種類数え上げる、指摘0件まで繰り返す、書き方の傾向に合わせるのを任意にする、適用までを既定にする）より、全体として良い設計があるか。

問いの選び方: ユーザーが「より良い全体最適を15分上限で思考実験する」と指定した（ユーザーの判断）。

## 前提

- **最終の結果:** 同じ基準で全体をもう一度判定しても、指摘が0件になる状態（不動点）。`d64ae13` がそうだとは確かめていない（未検証）。
- **1回で:** 利用者の呼び出しが1回。skill の中で何度繰り返してもよい。
- **全体:** skill の文章だけでなく、実行の構造（1人で判定するか、別の確認役を置くか）、入力（範囲、報告か適用か）、機械的な道具、試験を含む。
- モード: 構成的（全体の設計を組み立てる）。同時に、「5点の局所修正で足りる」を破壊的に攻撃する。選ばなかったもの: 探索的（発想を広げるだけで終える）。

対立仮説:

- H1 5点の局所修正で足りる。原因は skill の規則の欠け。
- H2 構造の問題。同じ1人が判定と完了の判断を兼ねると早く止まる。規則を足すより、別の文脈から全体を判定し直す確認役を置き、指摘0件まで回すほうが効く。
- H3 道具の問題。名前の網羅は文章の規則では強制できない。名前を全種類抜き出し、古い語を検索するスクリプトがあれば、網羅が選択の余地なく行われる。
- H4（本命の逆）skill は問題ではない。依頼（範囲、厳しさ、報告か適用か）が後から明らかになっただけで、直すべきは呼び出し方。あるいは、改名が新しい衝突を生むので1回で届くことは原理的にない。速く収束させることを目標にすべき。
- H5 分割の問題。判定の基準（Tellman の内容）と、コード全体を監査する手順（数え上げ・適用・繰り返し）を別の skill に分ける。

設定の欠陥:

- 「最終の結果」を、自分が4回かけて作った `d64ae13` に置くと、自分の作業を再現する skill を作ることになる（結論が設定に組み込まれる危険）。不動点という定義で避けるが、それを確かめる方法がまだない。
- 根拠はこの1回のセッションだけ（n=1）。
- 取りこぼしのうち、skill の規則の欠けによるものと、私が参照ファイルを読まなかったなどの実行のぶれによるものが混ざっている。

## 結果を攻撃する

本命: 「依頼の明示 ＋ 判定の揺れを抑える規則 ＋ 名前の数え上げの道具」の組み合わせ。

- **反例の思考実験（最強の反論）:** 揺れを抑える規則（既存の名前は判定表の行だけで判定し、迷ったら残す）を入れたとする。E1・E2 の `validate` → `errors` や `render` → `page` は判定表の行に当たらないので、出なくなる。結果は安定するが、変更は少ない側に寄る。ユーザーは「より厳格に厳しく」と求めた。厳しさを求める依頼に対して、安定のために変更を減らすのは、目標の取り違えになりうる。安定と厳しさのどちらを優先するかは、基準からは決まらない価値判断で、ユーザーが決めることになる。
- **原因の切り分けができていない:** 1回目の私は「依頼が曖昧」で、かつ「skill のファイルを全部読まなかった」。E1 は両方とも満たしていた。E1 が成功した理由がどちらなのかは、この試験では分けられない（ペアの試験をしていない）。
- **道具の一般性:** E2 の数え上げは、Python は構文木、JS と CSS は正規表現だった。skill は言語を問わないつもりで書かれているので、言語ごとに数え上げを書く必要がある。どの言語まで用意するかで、手間が変わる。
- **評価の的:** 「`d64ae13` と一致するか」は的として脱落。私の最終の状態は指摘0件ではなく、判定も試行ごとに割れる。測るなら「同じ条件で何回か回したときの判定の一致率」と「別の文脈で見直したときの指摘の件数」の2つになる。

## 結論

**暫定の結論（完了条件の3と4を満たしていないので、状態は「検討中」のまま）**

「1回の呼び出しで、唯一の最終結果に届く」ことは、定義上できない。同じ条件で3回かけると、判定が割れやすい25個の名前のうち、新しい名前まで一致したのは11個（44%）だけだった。基準は「その名前ではいけない理由」は出すが、「次の語」を1つには決めない。届けられるのは、次の2つ。

1. **1回の呼び出しの中で、自分で確かめた指摘0件の状態に届くこと。** E2（数え上げ＋繰り返し）が3回の繰り返しで届いた。
2. **一度決めた判定を、次の呼び出しが根拠なしにひっくり返さないこと。** 4回のやり直しの一部は、同じ名前を別の語に変え直していた（`checked` → `ref_read` など）。

そのため、全体の最適は「5点の局所修正」でも「揺れを抑えて変更を減らす規則」でもない。**規則（O1）＋ 数え上げと繰り返し（O2）＋ 判定の台帳（新しい案 H7）** の組み合わせになる。台帳には、名前ごとに、判定・新しい名前・根拠（判定表の行や規則）・日付を残す。次の呼び出しは、新しい根拠（判定表の行）があるときだけ、台帳の判定を変える。これで、厳しさを下げずに、呼び出しをまたいだ安定が得られる。段階C の最強の反論（安定のために厳しさを下げる）は、この方法なら避けられる。ただし、試していない。
