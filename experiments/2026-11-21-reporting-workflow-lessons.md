# セキュリティ報告ワークフローの知見化

- 状態: 設定中
- ゴール: 実務者（防災・政策）向けではない。**リポジトリ運用そのものの思考実験** — 今回のセッション（ブラウザのセキュリティのバグの発見・報告・類型化）から、他の課題にも先に適用できる判断基準を取り出す。変えうる判断は「Claude（と利用者）が次の課題の調査・報告をどう進めるか」。
- 開始: 2026-11-21
- 更新: 2026-11-21
- 関連: `designs/課題の理解の記録形式.md`、`~/firefox-credentialless-report/`（FORM-REPORT.md, FOLLOWUP-COMMENT.md, PATTERN-ANALYSIS.md、私的・非公開）

## 問い

今回のセッションから、他の課題にも移せる判断基準を取り出せるか。取り出したものは本物（結果を知る前に適用できる規則）か、後知恵か。

## 用語（取った読み）

- **知見**: 事実の要約ではなく、*先に*適用でき既定の振る舞いを変える判断基準。
- **本物**: 結果を知る前に適用でき、別の人が従えば同じ判断に至るもの。後知恵（結末を知ってから「こうすべきだった」）と区別する。

## モード

構成的（候補の基準を作る）＋破壊的な篩い（後知恵・自明を削る）。選ばなかった: 純粋破壊（攻撃対象が弱い）、説明的（起きたことの整理だけで価値が低い）。

## 価値の確認（段階A）

- **先行する答え**: 候補の多く（報告前に重複確認／公開前に機密判断／テストの交絡を疑う）は既知のソフト工学・セキュリティ運用の常識。→ 鋭い問いに変える:「既知原則のうち、今回*実際に効いた/破れた*のはどれで、既定の振る舞いとどう違ったか」。価値は新規性より「この文脈での具体化・境界・再現可能な失敗例」に置く。
- **実在する相手（破壊モード）**: 攻撃対象＝「結果が出た手順は最適だった」という私自身の事後説明。holder は私（このセッションで実際に下した判断）。藁人形回避のため、実際の判断を相手にする。
- **予想**: 情報通の実務者なら「本物は 2〜3 個、残りは既知の再確認」。確信=中。段階C でこの予想と比べる。

## 設定の欠陥

自分の作業を自分で評価する自己奉仕・後知恵バイアス。→ 段階C は fresh subagent に攻撃させる（`independent-attack.md`）。

## 対抗仮説（rivals）

- R1（本命）: 2〜3 個の本物の知見が取れる（既知原則の具体化＋実際に破れた手順）。
- R2（本命の逆）: 取れるのは後知恵の要約だけ。移せる規則は無い。
- R3: 全部すでに標準的な運用知識で新規性ゼロ（再確認）。
- R4: 知見は取れるが今回特有で、他課題に移せない（一般化不能）。

## 探り（1 条件を変える）

候補「報告前に重複を機械検索する」を、*結果前に適用できたか*で篩う。

- 事実: 2047854（本件そのものの既報）は Bugzilla の公開 API で見えたのに、私の最初の `dup_search`（症状語・部品語の query）は取り逃した。*ユーザーが「find similar issues」一覧を貼って*初めて判明した。
- 判定: これは後知恵ではなく*実際に破れた手順*。本物の知見候補 =「dup 検索の query 設計が弱かった（symptom/component 語だけでなく、トラッカーの『類似課題』機能や、修正済み・非公開も含む横断検索を先に回す）」。
- どの rival を支持: R1 を支持、R2/R3 を弱める（既知原則だが今回*破れ*、具体的な改善先がある）。暫定。

## 次の手（段階B 候補）

1. 候補基準を列挙し、各々を「結果前に適用可／既定と違う／別人で再現」で篩う。
2. *破れた*手順だけに絞る（dup 検索の取り逃し、初回の redact 過剰＝公開既報なのに履歴書き換えまで検討した）。
3. skill / 記録形式への反映（briefs 化）まで出す。
