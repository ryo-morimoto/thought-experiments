# ポート、登録可能なドメイン、localhost、不透明なオリジンの継承をモデルに入れると、結論と領域の十分さはどう変わるか

- 状態: 検討中
- 開始: 2026-11-24
- 更新: 2026-11-24
- 関連: [plan/browser-semantics-soundness/TREE.md](../plan/browser-semantics-soundness/TREE.md)、[experiments/2026-11-24-finite-domain-adequacy.md](2026-11-24-finite-domain-adequacy.md)（データ独立の条件）、[adequacy/](models/site-isolation/adequacy/RESULTS.md)
- 木の節: browser-semantics-soundness/B7

## 問い

データ独立の議論は、モデルが写した演算子（等しさ、同じサイト、スキーム、同じホストの片割れ）に限られた。モデルが写していないオリジンの構造（ポート、登録可能なドメインの計算と公開の接尾辞の一覧の違い、登録可能なドメインの無いホスト、localhost の安全な文脈、about:blank・srcdoc・blob・sandbox の不透明なオリジンの継承）をモデルに入れると、性質の判定は変わるか。関係の型はどう増え、どの大きさの領域が要るか。入れないものは、入れない理由と、結論がどの範囲に限られるかを書く。

問いの出し方（ユーザーの判断）: 作業の木の効きが高・中の節がなくなるまで進める（/goal）。Claude は、互いにぶつからない作業の束に分けて並行で進め、この記録はその束の 1 つ。

## 前提

- 仕様: URL の origin と site と schemelessly same site、HTML の obtain a site、same site、secure context、不透明なオリジンの作り方と継承。
- モード: 構成的。

対立仮説:

- R1 判定は変わらない。構造を入れても、性質は今の書き方で成り立ち、関係の型の数が増えるだけ。
- R2 判定が変わる。ポートやサイトの計算を入れると、ある性質が崩れる（例: 同じサイトで別オリジンのポートの間の CORP same-site）。
- R3 一部は入れられない。公開の接尾辞の一覧がクライアントで違うことは、パラメータとしてしか扱えない。

設定の欠陥: 入れる構造の範囲は筆者が選ぶ。

## 条件を変える

subagent が、SpecIsolation を変えずに広げたモジュールで、オリジンを（不透明か、id、スキーム、ホスト、ポート）にし、サイトを公開の接尾辞の一覧の抽象の関数から計算し、仕様の演算子（スキームを問わない同じサイト、obtain a site と same site、潜在的に信頼できるオリジン、不透明なオリジンの作り方と継承）を書き、性質を書き直して検査した（[originstruct/](models/site-isolation/originstruct/RESULTS.md)、OriginStruct.tla、types2.py）。Secure Contexts と Mixed Content の編集者草案は 2026-11-24 に取得。筆者は報告を読んだ。

**結果**: 仕様の演算子で書き直した性質（同意の性質 3 つは CorpPermitsR で結ぶ、COI の上と入れ子、エージェントクラスタの鍵と不透明なオリジンの新しい性質）は、関係の型をすべて実現する領域（63 個のオリジン）で、公開の接尾辞の一覧の 2 つの版のどちらでも真。NoHeaderLeak は前と同じく偽。

**判定が変わったもの**（どれも、前の読みを持ち越した演算子）

| 構造 | 変わったもの | 反例 |
| --- | --- | --- |
| ポート | エージェントクラスタの鍵。A1 で直した KeyHTML もポートを落とすので、隔離のもとで https://x.a.test と https://x.a.test:8443 が同じ鍵になる | 前の Key は https と http も衝突させる |
| ポート（ほか） | 崩れない。同じサイトで別オリジンのポートの間で、require-corp のもと CORP 無しは誤り、same-site は不透明、COOP same-origin の popup は切れる | |
| 公開の接尾辞の一覧の違い | クライアントが一覧 A、作者が一覧 B を想定すると、https://a.test が https://x.a.test から CORP same-site の不透明な応答を受ける（逆向きは止める側だけ） | |
| localhost | http://localhost と http://127.0.0.1 は cross-origin isolated になりうる。http://127.0.0.1 は混在の中身ではない。CORP のスキームの条件を「信頼できる」で読む変異体は、安全な文脈の性質を崩す | |
| 不透明なオリジン | gen2 の 1 つの定数は、新しさの性質を崩す。about:blank の COEP をヘッダーだけで取るか、安全な文脈を文書自身のオリジンで取ると、継承の性質が崩れる | |

- 2 つの仕様の本文をまたいだ読みで、性質が 1 つ偽になった。ブラウザでは確かめていない。仕様の本文の穴の読みを伏せるユーザーの判断に沿い、その性質と反例はリポジトリから外し、利用者の非公開の場所に置いた（作業の木の F8 に加えた）。
- 関係の型: k = 1 で 9、k = 2 で 194、k = 3 で 6,501。前の 18 個の領域は 6,501 のうち 96 しか実現しない。63 個の領域（https の片割れについて閉じる）はすべてを実現する。型は公開の接尾辞の一覧に依らないので、許される一覧の 1 つで型を実現する領域は、どの一覧も覆う（議論で、証明ではない）。
- 入れていないもの: document.domain、file: と設定で信頼するオリジン、公開の接尾辞の一覧の算法と IDNA と IPv6、sandbox の旗の継承と allow の語、popup と worker、blob の失効と分割、2 つ以上の祖先の Mixed Content、広げた領域での NoUndeclaredLeak（約 1.4 億の場合）。

読み取れること:

- R1（判定は変わらない）は、仕様の演算子で書き直した性質について当たった。
- R2（判定が変わる）は、前の読みを持ち越した演算子（前の Key、A1 の KeyHTML、CORP のスキームの条件を信頼性で読むこと、1 つの不透明な定数、ヘッダーだけの COEP、文書自身のオリジンからの安全な文脈）について当たった。A1 の直し（KeyHTML）にもポートが要る。
- R3（パラメータとしてしか入らない）は、公開の接尾辞の一覧について当たった。クライアントと作者の一覧が違えば、どの 1 つのモデルの外にも出る。
- 前の 18 個の領域は、仕様のオリジンの構造の関係の型をほとんど実現していなかった（6,501 のうち 96）。A2 の結論は、モデルが写した演算子に限ったことで成り立っていた。
