# ブラウザの意味論から検証モデルへの変換に、健全性の根拠を与えることができるか

- 状態: 検討中
- 開始: 2026-11-20
- 更新: 2026-11-21
- 関連: [experiments/models/site-isolation/](models/site-isolation/SOURCE.toml)（TLA+ モデル）

この記録は、会話の後半（2026-11-21）にまとめて書いた。段階ごとのコミットはしておらず、途中経過は会話の記録から再構成した。

## 問い

ブラウザの意味論（WHATWG などの散文仕様と、それを実装したブラウザ）を Alloy や TLA+ などの検証モデルに変換するとき、「モデルで安全なら実際のブラウザでも安全」と言える根拠を与えられるか。

問いの出し方（ユーザーの判断）: スキル running-thought-experiments の引数として、この問いをそのまま与えた。

## 前提

- **健全性**: モデルが性質 P を満たすなら、実際のブラウザも P を満たすこと（過近似）。安全性性質なら「実装の振る舞い ⊆ モデルの振る舞い」が要る。逆向きの「見つけた反例が実際に起こる（誤検知がない）」とは区別する。
- **根拠**: 証明と経験的な裏付けの両方を含むと読んだ。
- モード: 構成的かつ開いた問い。条件つきなら健全性を組み立てられることを、1 つの例で示せるかを試す。採らなかった候補は、破壊的（既存の変換に反例を探す）と例示的。

対立仮説（段階A）:

- R1 不可能。変換元が形式的でないので、証明は原理的にできない。
- R2 相対的に可能。機械化した参照意味論を間に置けば、それに対する健全性は定理にできる。
- R3 性質を限れば可能。
- R4 逆向きが筋。健全性は諦め、反例を実ブラウザで再生できることだけを根拠にする。
- R5 根拠の本体は仮定。健全性は「変換＋仮定の集合」の性質である。
- R6（段階B で追加）単一ソース化。SpecTec のように、形式記述から散文を生成すれば第1層を構成で閉じられる。

設定の欠陥: 「根拠」が証明か証拠かを決めていない。ブラウザは 1 つではない。

## 条件を変える

段階B の操作は「経過」に日付順に書いた。主な結果は次のとおり。

- 先行研究（調査を委任し、報告を読んだ）: ブラウザのモデル（Akhawe ら 2010、WebSpec、Featherweight Firefox、WebSpi、FKS）は、どれも変換の健全性を証明していない。JS と Wasm の機械化は二層構造をとる。第1層「散文と参照意味論の対応」はテストで、第2層「参照意味論の上の性質」は証明で支える。
- 非決定性: WPT 型のテストは反例の実在性しか支えない。実装のトレースを参照意味論と照合するトレース検証なら、包含の向きを（観測した範囲で）支えられる。
- implementation-defined: WHATWG には C 言語のような区別がない。何に裁量があるかで扱いを分ける（値と構造はパラメータ、実行時の方策は安全性性質なら非決定性、仕様の欠落は対象外）。
- 合成: メッセージで繋がる部分は、通信路ごとの不変条件に分解できる。共有メモリは小さな範囲でしか検査できない。プロセス分離は仕様の外にある。

## 結果を攻撃する

1. 自分で攻撃した（段階C、2 回）。2 回目に、「実装の状態数に上限があり、実行が公平」という仮定を「結論の先取り」として消去した。
2. ユーザーの指摘（ユーザーの判断）: 「全て知ってるエージェントだと判断をミスる確率が高くなる」。経緯を渡さない新しい subagent 3 体（形式手法・ブラウザセキュリティ実務・科学哲学）に攻撃させた。3 体が独立に、1 の消去が誤りだったこと（その仮定は普通の理想化で、結論を含意しない）を指摘した。消去を取り消した。
3. 段階B で出した「②は G と O に分解できる」という主張も、新しい subagent 3 体（形式手法・Chromium 実務・バグ履歴）に攻撃させた。O が攻撃者のいない問題でないこと（CVE-2024-9392）と、プロセス配置が仕様の外にあること（CVE-2018-16073、CVE-2018-16074）で崩れ、D′ に改めた。
4. D′ の一部を TLA+ のモデルで検査した（「具体」に出力）。
5. D′ を新しい subagent 3 体（形式手法・ブラウザセキュリティ実務・保証ケース）に攻撃させ、D″ に改めた（「結論」の「②の改訂」）。並行して、モデルに J と S′ の (b) を加えた。

## 結論

暫定。②は D′ を新しい subagent 3 体に攻撃させ、D″ に改めた（下の「②の改訂」）。D″ はまだ攻撃を受けていない。

問いは、そのままでは定まらない。参照意味論 R、観測する事象 Σ、脅威モデル T、構成 c を固定すると、答えは性質の種類で分かれる。

| 対象 | 答え | 根拠の形 |
| --- | --- | --- |
| ① Σ 上の安全性性質（攻撃者のいない脅威モデル） | 与えられる | 信頼する部分を明示した条件つきの定理（CompCert と同じ種類）。R の忠実さはトレース検証で支え、網羅率は「証明が使った制約ごとに、違反がありえた場面で、変異させたトレースを検査器が拒否した回数」で測る |
| ② 乗っ取られたレンダラーのもとでのセキュリティ性質 | 大域的な健全性の定理としては与えられない | D″: 資源の種類ごとの、版つきの契約（下の「②の改訂」）。各項目を、設計に合った種類の証拠で支える保証ケースになる |
| ③ 機密性の超性質（サイドチャネルを含む） | 包含にもとづく健全性の対象外 | 未解決 |

### ②の改訂（D′ → D″）

D′ は「G′（ガード）・I\*（信頼状態の完全性）・L（プロセス配置の方針）・J（割り込みでの不変条件）がそろえば S′ が成り立ち、証拠は攻撃者を想定したものでなければならない。WHATWG は I\* の中でオリジンの値の部分的な判定基準になるだけ」と主張した。新しい subagent 3 体（形式手法・ブラウザセキュリティ実務・保証ケース）の反論と判定:

D″（3 体の対案を合わせたもの）: ②について大域的な性質 S′ を正当化することはできない。正当化できるのは、資源の種類（フレーム、クッキー、ストレージ、資格情報、メッセージ）ごとの、リリースの版つきの契約である。各項目に、主体（StorageKey・COI を含む）、強制する箇所、信頼の仮定（GPU やネットワークのサンドボックスを含む）、既知の穴を書き、設計に合った種類の証拠（構造の点検、攻撃者を想定したファジング、有界のモデル検査による設計の反例探し）で支える。反証要因の一覧と、証拠を取り直す契機を持つ。Chromium の compromised-renderers.md はこの形で書かれている（実務の subagent が確認）。WHATWG は性質の語彙を与え、配置の方針と強制はブラウザの設計が与える。

前提の種類:

1. 定義上: 健全性は R・Σ・T・c に相対的に決まる。
2. 経験的（文献の報告を読んだ）: ブラウザについて変換の健全性を証明した研究はない。JS・Wasm の機械化、seL4、CompCert は、信頼する部分を明示した条件つきの定理である。
3. 論証: T が実装の乗っ取りを含むと、仕様から作った参照意味論は、実装の振る舞いを縛る根拠としてはほとんど寄与しない。ただし性質の語彙（オリジン、Fetch で渡ってよいもの）は仕様が定める。
4. 論証: 散文と R の隙間は、どの層でも閉じない。仕様が実装を後追いするので、R は実装間の合意を経験的に記述したものになる。
5. 論証（玩具モデルで確認）: ②では、ガードが健全でも、信頼する状態の完全性（I\*）、配置の方針（L）、検査と使用の不可分性（J）のどれが破れても性質が破れる。正直なトレースだけでは I\* の破れは見えない。ロックに相対的な S は、ロックの割り当ての誤りを見逃す。これらは玩具モデルでの必要性で、コードでの十分性ではない。

生き残った選択肢:

- a″ 上の表（①〜③で答えを分ける）
- b 反例の実在性だけを根拠にする（R4）。費用が低く、攻撃の発見に向く
- c 参照から実装を導出する（R6、Quark）。問いを「構成による健全性」に置き換える

脱落した選択肢（理由つき）:

- R1 の「根拠が何もない」という読み: 条件つきの定理は立つ（JaVerT、Iris-Wasm）。
- 「非決定性として持てば常に健全」: 超性質では成り立たない。
- 「implementation-defined はパラメータ、unspecified は非決定性」: Infra にも HTML にもその区別がない。
- 「テストは反例の実在性しか支えない」（一般論として）: トレース検証は包含の向きを支える。
- a′ の「第2層は定理、第1層は経験仮説」という種類の区別: seL4 などと同じく、違いは網羅率・決定性・観測の完全さの程度である。
- 「仮定は局所的で反証可能であるべき」という規則: 補助仮説が独立に反証できない（Duhem–Quine）。「信頼する部分を明示する」に置き換えた。
- 「π（エージェントクラスタからプロセスへの対応）は関数」: 履歴と構成に依存する関係である。
- 「O（信頼状態の計算）は攻撃者のいない問題で、仕様に対するトレース検証で足りる」: CVE-2024-9392 で、IPC の値が信頼する状態に書き込まれた。
- 「入力の文字が有限なので、検査の欠落は構造的に見つかる」: どのメッセージにどの検査が要るかの対応表が書かれていない。権限つきのハンドルや、IPC を通らない経路がある。
- D′ の「WHATWG は I\* の中の部分的な判定基準にすぎない」: 仕様は性質の語彙そのものを定める。
- D′ の「証拠は攻撃者を想定したものでなければならない」（一般論として）: 偽造できないハンドルの設計では構造の点検で足りる。
- ②についての大域的な性質 S′ を正当化できるという前提: L が固定できず、主体がオリジンだけでは足りない。

### 仕様の引用

Infra Standard（https://infra.spec.whatwg.org/ 、2026-11-21 取得）:

> If something is said to be implementation-defined, the particulars of what is said to be implementation-defined are up to the implementation.

HTML Standard（https://html.spec.whatwg.org/ 、2026-11-21 取得）のイベントループ:

> Let taskQueue be one such task queue, chosen in an implementation-defined manner.

> Task queues are sets, not queues, because the event loop processing model grabs the first runnable task from the chosen queue, instead of dequeuing the first task.

本文テキスト中の語の数（筆者が html.spec.whatwg.org の本文から数えた）: implementation-defined は 84 回、unspecified は 8 回（非決定性の意味で使うのは「run in an unspecified order」の 2 回だけで、残りは「まだ仕様化されていない」の意味）。

### TLA+ モデルの検査

モデル: [models/site-isolation/SiteIsolation.tla](models/site-isolation/SiteIsolation.tla)。攻撃者のサイト A と被害者のサイト V、プロセス 2 つ、フレーム 2 つ（トップとその子）。A にロックされたレンダラーが乗っ取られる。

- S: プロセス p のデータアクセスは、すべて p のロックに許されている。
- GuardSound: IPC で許したアクセスは、すべてガードの検査を通っている。

実行したコマンド（ディレクトリ `experiments/models/site-isolation` で。CFG を差し替えて実行）:

```sh
podman run --rm -v "$PWD":/spec:Z -w /spec localhost/veda-tlc:1.8.0 \
  java -XX:+UseParallelGC -cp /opt/tla2tools.jar tlc2.TLC -metadir /tmp/states -config <CFG> SiteIsolation.tla
```

2 回目（2026-11-21）に J と S′ の (b) を加えた。S は「アクセスした時点のロックが許していた」に定義し直した（ロックされていないプロセスは、どのサイトも許す）。最初の定義（現在のロックとの等号）は、ロックされていないプロセスを常に違反とみなしていた。以下は定義し直した後の、TLC2 Version 2026.10.28.014557 の出力。

CVE9392.cfg の反例: `Navigate("top","A")` で p1 が A にロックされる → `ReplaceState("top","V")` で、乗っ取られたレンダラーが履歴を V に書き換える → `Reload("top")` で、ブラウザは履歴を自分のフレームの URL と信じて同じプロセスで読み込む。最終状態は `access = {<<"p1","A">>, <<"p1","V">>}`、`lock = [p1 |-> "A", ...]`。

B2.cfg の反例: `Navigate("top","A")` → `Restore("V")` で、キャッシュから戻した子フレーム（V）が親のプロセス p1 に置かれる。`access = {<<"p1","A">>, <<"p1","V">>}`。

TOCTOU.cfg の反例: `Navigate("top","A")` → `BeginRequest("top")`（検査の時点ではフレームのオリジンは A で、ロックと一致） → `Navigate("top","V")`（V はロック済みの p1 に置けないので p2 に移る） → `CompleteRequest`（使用の時点のオリジン V のデータを、要求元の p1 に渡す）。

LateLock-Witness.cfg の証人: `Navigate("top","A")`（p1 はロックされないまま A を動かす） → `Navigate("top","V")`（p1 が V にロックされる）。この状態で `violations = {}`（S は成り立つ）だが、`hosted[p1] = {"A","V"}` で、攻撃者のコードが残る p1 は V のデータをガードを通って正当に要求できる。

読み取れること:

- ガードが健全でも（GuardSound は 987 状態すべてで成立）、I\* が破れると S が破れる。G′ だけでは足りない。
- 同じ欠陥のあるコードでも、攻撃者の IPC がない正直なトレースでは違反が出ない。仕様に対するトレース検証では I\* の破れを見つけられない。
- 配置の方針 L だけが違うと、ガードもオリジンの計算も同じなのに S が破れる。
- 検査と使用が不可分でないと、検査の時点では正しい要求が、ナビゲーションを挟んで別オリジンのデータを渡す（J）。
- ロックに相対的な S は、ロックの割り当ての誤りを見逃す。S′ の (b) が要る。ただし (b) は L を書けてはじめて意味を持つ。

モデルの限界: 破棄の順序や、データ要求以外のメッセージの割り込みは扱っていない。サイトは 2 つ、プロセスは 2 つ。オリジンとサイトを同一視し、StorageKey や cross-origin isolated の区別はない。Fetch で正当に渡る別オリジンのデータ（no-cors の画像など）は表していない。コードとの詳細化の対応はなく、示せるのは玩具モデルでの必要性だけ。
