### taint_path（部品: セキュリティ）

- steps:
  1. 攻撃者の HTTP サーバが `Location:` に長いホスト名を返す（`CURLOPT_FOLLOWLOCATION` が前提）。**行の指定なし**（報告は機能名で書く）
  2. URL の解析でホスト名の長さ ≤ 65535 が保証される（`url.c` 1808–1811）
  3. `do_SOCKS` が局所変数を初期化（`socks.c` 573–574）、初回だけ長さ > 255 で TRUE にする（588–593）
  4. hello の待ちで戻り、再入で局所変数が FALSE に戻る（640–662）。**データの流れではなく、状態と時間の段**
  5. `CONNECT_REQ_INIT` から遠隔解決へ（781–797）
  6. `memcpy` で長さ無制限に複写（904–911）
- value_condition: `255 < hostname_len ≤ 65535` かつ `hostname_len > buffer_size + 1 − 5`（先頭 5 バイトの見出しの後に書くため。報告は「残りの大きさを超えれば」と書く）。既定の `buffer_size = 16384` で成立、curl ツールの既定 102400 では不成立。
- 本文の数値との照合: 16384+1 < 65535 < 102400+1（#0 の本文）は定数と整合。R2 の `0x4025` = 16421 は 16385 と 36 違う。報告者は「ヒープの保護バイト」と説明する。機械で数値を照合すると、**ここは不一致として出る**（デバッグビルドの割り当ての上乗せは、ソースの定数からは導けない）。
- **【摩擦】** 第 2 版の `taint_path.steps` は「入力から問題の行までの段」で、各段に行を求める。本件の欠陥の核心（段 4）は、データの値ではなく**状態機械の再入で局所変数が失われる**ことで、汚染の経路の形に収まりにくい。段 1 は機能（`CURLOPT_FOLLOWLOCATION`）で書かれ、行が無い。

## 比較: 観測の無い本物の報告（2559516、本文だけ）

- 本文: コミット `04739054` の `lib/vtls/x509asn1.c` 397 行で、関数内の配列 `char buf[4]` に `free()` を呼ぶ、という指摘。コードの抜粋（途中を省略）、悪用の筋書き（悪意のあるサーバの TLS 証明書 → 接続時の解析 → スタックの番地が空きリストへ）、1 行を消す修正案、重大度 High の主張。**クラッシュの出力も、試験も、証明書も無い**。
- 結末: 妥当として受け入れ、Medium、2540 USD。勧告は「最もありうる結果はクラッシュ」とし、到達する TLS の実装（GnuTLS、wolfSSL、Schannel、Secure Transport、mbedTLS）を限定した。報告はこの限定を書いていない。
- コードの位置の照合: curl 8.8.0 の配布物（sha256 `77c0e1cd35ab5b45b659645a93b46d660224d0024f1185e8a95cdb27ae3d787d`）では、同じ `free(buf)` は **393 行**にある。報告の差分の `index cea88e668..` は 8.8.0 の blob（`4564ea958a…`）と違う、つまり報告の版は 8.8.0 と別の版。指定のコミットのファイルそのものは、この作業の取得経路の制約で機械照合できていない（未照合）。**近い版で照合すると、行がずれて「不一致」と出る**。
- 値の条件: 報告は書いていない。抜粋から導くと「UTF8String 以外の型（例えば 4 バイトの文字）で、文字の値 ≥ 0x200000」（推論）。

## 規則の修正案（証拠つき）

1. **規則 2 を「観測 または 機械照合を通った因果の経路と値の条件」に緩める。** 欠陥の成否を値の条件で書ける主張は、各段の引用が機械照合を通り、値の条件が既存の検査と矛盾しなければ、観測なしで「人が読む」へ回す。根拠: 2187833 の妥当性は再実行なしで 33 分、2559516 は観測なしで受け入れ。偽の 2298307 はこの経路では値の条件が 579 行と矛盾して止まる。
2. **欠陥の種類で `taint_path` の役割を分ける。** 境界・長さの欠陥（溢れ、読み過ぎ）は、欠陥の成否が入力の値に依存するので、妥当性に経路と値の条件を要る。スタックの `free`、二重解放のように**到達すれば必ず誤り**の欠陥は、妥当性には到達の有無だけを求め、経路の細部は深刻度（`judgment.severity.preconditions`）へ回す。根拠: 2559516 は経路の段を書かずに受け入れられ、到達する TLS の実装の限定は保守者が勧告で足した。
3. **「既存の検査の名指し」を `taint_path` に足す。** `guards = [{ at = "コミット・パス・行", why_bypassed = "" }]`。問題の行の手前にある検査を機械で拾い、報告にその説明が無ければ最初の問いとして返す。根拠: 偽の報告への保守者の最初の問いと、本物の報告が本文で先に答えていた箇所が同じ形。
4. **`taint_path.steps` に段の種類を足す。** `kind = "data" | "state" | "config"`。状態や時間で成り立つ段（2187833 の段 4）と、設定で入口が開く段（段 1、#29 の環境変数）を書けるようにする。行は data と state の段に求め、config の段は文書（オプションの説明）でよい。
5. **規則 3 の位置はタグ・リリースも受け、照合器がコミットに解決する。** 照合は必ず指定の版で行い、近い版で代用しない。差分の `index` 行の blob が分かれば、版の確認に使う。根拠: 2187833 はタグで 9/9 一致、2559516 は 8.8.0 で照合すると 4 行ずれる。
6. **値の照合で不一致が出たら、棄却ではなく `question` にする。** 報告者が説明（「保護バイト」）を付けていれば、説明ごと人に回す。根拠: `0x4025` の 36 バイト差は、ソースの定数からは導けないが、欠陥の成否には効かない。
7. **観測の再現に対象の書き換えを使う場合、書き換えの種類を記録する。** 時間・スケジュールだけを変える（遅延の注入）なら観測として数え、論理を変えるなら数えない。根拠: 2187833 の遅延の書き換えは `return CURLPX_OK` を 1 回挟むだけで、修正には試験も付いた（#58）。
