## なぜこの課題か

「Pod が Terminating のまま消えない」という症状だけで集まった課題で、「同じ問題です」というコメントが 4 年で 190 件近く付いた。後から見ると、中身は少なくとも 8 種類の別のバグや設定の問題だった。そのうち 2 つは、このスレッドのコメントが手がかりになって別の課題に結び付けられ、直った（1 つは既存の課題、1 つは新しく切り出した課題）。重複の判定と、重複からの情報の集め方を試すのに向く。

コメントの年ごとの数（筆者が GitHub API で数えた）: 2017 年 26、2018 年 89、2019 年 41、2020 年 26、2021 年 6、2022 年 3。

以下、コメントは `c番号`（API が返す順の通し番号）で書き、リンクは `https://github.com/kubernetes/kubernetes/issues/51835#issuecomment-<ID>` の形にする。

## 実際の結末（as_of 以降）

- **E は 2 日後に解決した。** メンテナが c42 で 61178 を指した。

  > For folks seeing this issue on 1.9.4-gke.1, it is most likely due to https://github.com/kubernetes/kubernetes/issues/61178, which is fixed in 1.9.5 and is being rolled out in GKE this week.

  https://github.com/kubernetes/kubernetes/issues/51835#issuecomment-376957410

  61178 は as_of の 1 週間前（2018-03-19）に閉じていて、1.9 系の修正 PR の題は「lstat with abs path of parent instead of '/..'」だった（https://github.com/kubernetes/kubernetes/pull/61193 ）。E のエラー文（`lstat .../..: not a directory`）と PR の題が文字どおり一致する。**エラー文で既存の課題を検索していれば as_of の時点で見つかった**（推論）。
- **「直った」報告は当てにならなかった。** c45 で E の 1 人が「1.9.6 で直った」と書き、c47 で同じ人が「早とちりだった」として再び止まった Pod を示した。c47 に載っているのは `Need to kill Pod` のイベントだけで、ログのエラー文が無いので、E が残っていたのか別のバグなのかは分からない。
- **シンボリックリンクの群は、重複のコメントが鍵を出した。** c91（コントリビュータ、1.10.2）は subPath の後始末で `device or resource busy` を報告し、同じ人が c92 で、`/var/lib/kubelet` をシンボリックリンクにしていたことと、`--root-dir` で直接指すと Pod が消えたことを書いた。約 1 か月後にメンテナが 68740 を起票し、本文で条件をはっきり書いた。

  > If you don't have a symlink, then it's a different bug.

  https://github.com/kubernetes/kubernetes/issues/68740

  修正は https://github.com/kubernetes/kubernetes/pull/68741 。決め手は、ログのエラー文ではなく**消えた操作**（`--root-dir` に変えたら直った）だった。
- **その他の群**: glusterfs（c51）と Ceph（c62）はメンテナが「別のバグ」として新しい課題を求めた（c52 は「this signature looks different from the others.」、https://github.com/kubernetes/kubernetes/issues/51835#issuecomment-383435366 ）。NFS のサーバーを先に消すと unmount が止まるのは既知の制約とされた（c131）。secret が存在しない（c84）、containerd 1.4 の shim（c179、containerd#4656）、作ってすぐ消す競合（PR #98424）も別の原因だった。起票者の A の原因は最後まで特定されなかった（c42 は「containerized kubelet の設定の問題と理解している」と書いたが、起票者は kops で、kubelet の動かし方は答えていない）。
- **閉じ方**: メンテナが「対象が広すぎて直せない」として閉じ、詳しいログを付けた新しい課題を求めた。

  > There are many possible reasons why a Pod could get stuck in terminating. We know this is a common issue with many possible root causes! :)

  https://github.com/kubernetes/kubernetes/issues/51835#issuecomment-780923556

## 評価

### same_bug_condition と related.merge は見分けに役立ったか

- **役立った点**: 「症状を条件にしない、ログの最初のエラー文と環境で判定し、ログが無ければ判定しない」と書いたことで、as_of の 39 件は A〜F に分かれ、E を独立の群として取り出せた。E を 51835 にまとめず別に扱う判断は、実際の結末（61178）と一致した。c47 のような「ログなしの再発」を判定しない（まとめない）既定も正しかった。
- **足りなかった点 1**: 条件が課題全体に 1 つしか書けない。51835 は 1 つのバグではなく症状の入れ物なので、条件は**群ごと**に要る。results の表で群を作ったが、形式にその欄は無く、表の 1 列として無理に入れた。
- **足りなかった点 2**: シンボリックリンクの群（68740）は、エラー文では A'' や C と区別できなかった（どれも `device or resource busy`）。区別したのは**何をしたら消えたか**（`--root-dir`、`fs.may_detach_mounts`、Docker の再起動、mountinfo で見つけたプロセス）だった。消えた操作は、原因の仮説を直接確かめた介入の結果で、ログより強い証拠だった。形式では results の `result` に紛れ込む。
- **足りなかった点 3**: `related.merge` は「受け手がまとめるか」を前提にしているが、この課題で起きたのは**報告者が自分で合流する**ことだった（「same issue」のコメント）。必要なのは、まとめる・まとめないの二択でなく、「仮に入れておく（未判定）」「分けて新しい課題にする」を含む状態。
- **足りなかった点 4**: 重複の確認を「したか」が残らない。E の答えは as_of の時点で別の課題にあった。どの言葉で、いつ検索したかを残す欄が無いと、「重複の確認: 確認済み」を信用できない。

### 多数の重複の情報をどう集めるか

results を環境の並びにすると、群・報告の数・最初に見た版・直ったという主張の真偽が入らない。この課題で判断を動かした情報は次の 4 つだった。

1. **エラー文の指紋**（E を 61178 に結んだ）。
2. **消えた操作**（68740 と moby#22260 を結んだ）。
3. **版の範囲**（E は 1.9.4 で始まり 1.9.5 で消えるはず、という予測が立つ）。
4. **どの報告が何を足したか**（c92 が 68740 の起点、c33 が mountinfo の調べ方、c24 が「2 つの別のバグ」という最初の分割）。

「同じです」だけの報告（F）は数を数えるだけでよく、内容を記録しても判断を動かさなかった。

## 未確認

- 起票者の A の原因（H2）。起票者は c33 の手順を試していない。
- c26 の「初期化と削除の競合」と PR #98424 が同じバグか。#98424 は CRI-O と cgroup の後始末の競合で、c26 は Docker と NFS なので、別の可能性がある。
- 群の分け方は筆者が c1〜c39 を読んで決めたもので、別の人が分けて一致するかは確かめていない。
- `[[report]]` を 190 件すべてに書くのは重い。指紋か消えた操作がある報告だけを書き、残りは群ごとの数にする運用を想定しているが、1 件にしか当てていない。
