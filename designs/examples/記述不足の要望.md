# 例: 記述不足の要望（ripgrep の `-M` で長い行の先頭を見せる）

- 状態: 試案の検査（1 件）
- 作成: 2026-11-21
- 対象の形式: [課題とバグの理解の記録形式](../課題の理解の記録形式.md)
- 種類: 期待する動作がはじめ定まっていない、または争われていた機能要望・動作変更の要望

試案はバグのために作った。これを、解決済みの公開の機能要望 1 件に当てて、どの欄が使えて、どの欄が使えず、何が足りないかを見る。

## 選んだ課題

- URL: https://github.com/BurntSushi/ripgrep/issues/1078 （2018-10-05 起票、2019-04-14 にコミットで閉じた）
- 閉じたコミット: ece1f50cfe49fea324d96f97a2ae00ebbd0cad03（`printer: support previews for long lines`）。閉じた後に ef1611b5f5 でフラグ名を `--max-column-preview` から `--max-columns-preview` に直した。
- 選んだ理由:
  - 要望が「ag（the silver searcher）のようにしてほしい」という、他の実装を基準にした動作変更の要望である。
  - 要望の中身（長い行の先頭を見せる）は例つきで具体的なのに、**既定を変えるのか、別の選択肢にするのか**、末尾の印をどうするか、という点が争われた。
  - 途中で別の要望（一致の前後だけを残す切り詰め）が混ざり、保守者が範囲外とした。
  - 結論（既定は変えず、新しいフラグで先頭を見せる）がコミットと試験で残っている。閉じた後も、フラグの使い方が利用者に伝わらない問題がスレッドに続いた。

コメントの番号は、起票本文を #0、以降をスレッド上の順に #1, #2, … と数える。人は役割で呼ぶ（起票者、保守者、貢献者 A、利用者 B など）。

## 起票時点（as_of = #0）で形式を埋める

起票本文だけを見て埋めた。判断の欄はエージェントの下書き。**【摩擦】** は形式がこの種類の課題に合わなかった箇所、**（推論）** は筆者の推論。

### meta

- source: https://github.com/BurntSushi/ripgrep/issues/1078
- as_of: #0（2018-10-05T04:08Z の起票本文のみ）
- versions: ripgrep 0.10.0（Homebrew、macOS 10.13.6）。比較対象の ag の版は書かれていない。

### claim

- question: なぜ `-M 15` を付けると、長すぎる一致行が中身の分からない一行（`[Omitted long line with 1 matches]`）に置き換わるのか。
  - **【摩擦】** 「なぜこうなったか」の答えは「設計どおり」で、原因の探索に進まない。要望で問うべきは「状況 S で、利用者が目的 G を果たすには、何が表示されるべきか」である。起票者の目的は本文にある: 「この行が生成された JavaScript かどうかを見分けたい」（要約）。この目的を書く欄が無い。
- observed: `-M 15` で長い一致行が、件数だけを示す一行に置き換わる（起票本文の例）。
- expected: 行の先頭の 15 文字ほどを表示し、続きを省いたことを示す（ag の `-W 15` の出力例のように `[...]` を付ける）。
- expected_basis:
  - 他の実装: ag の `-W`（起票者の記述。確かめていない）。
  - 利用者の目的: 生成されたコードかどうかを先頭で見分けたい。
  - **【摩擦】** 試案の選択肢（仕様の箇所、以前の動作、他の実装、思い込み）には「利用者の目的」と「同じ道具の他の選択肢との一貫性」が無い。後者は #2 で貢献者 A が持ち出した根拠で、保守者の判断に効いた。
- expected_status: 未確定（下書き）。
  - **【摩擦】** 1 つの値では足りない。この課題では「何を表示するか」は例つきで分かる（記述不足ではない）。決まっていないのは「既定を変えるか」と「細部（印の文言、数え方の単位、色）」で、前者は**記述の不足ではなく合意の不在**である。試案は両者を `記述不足` 1 つにまとめてしまう。

### reproduction

- artifact: なし（起票本文の 3 つのコマンドと出力）。
- steps: 長い行に一致する語を `rg -M 15` で探す。
- same_bug_condition: **【摩擦】** 該当なし。現在の動作は設計どおりで、だれが試しても同じ結果になる。
- results:
  - ripgrep 0.10.0: 長い行を件数だけの一行に置き換える（起票者の観測）。
  - ag（版不明）`-W 15`: 先頭 15 文字ほど＋`[...]`（起票者の観測。未確認）。
- regression_range: 該当なし（以前から設計どおり）。
- 評価: 「比較対象の環境も入れる」という results の書き方は、**参照する実装の動作を確かめる欄**としてそのまま使えた。後で分かるとおり、保守者はここを確かめるのに手間取った（#7）。

### evidence

|---|---|---|---|

| E2 | 観測（起票者） | ag の `-W 15` は先頭を表示し `[...]` を付ける | 起票本文の出力例（#0）。起票時点で第三者は確かめていない |

### hypothesis / diagnosis

**【摩擦】** 原因の仮説は立たない（設計どおりの動作なので）。代わりに要るのは**設計の選択肢**と、それぞれを評価する観点である。起票時点で下書きできた選択肢（推論）:

| id | 選択肢 | 起票者の目的を満たすか | 既存の利用者への影響 |
|---|---|---|---|
| O1 | `-M` の既定の動作を ag のように変える（起票者の要望そのもの） | 満たす | `-M` を使う既存の利用者の出力が変わる |
| O2 | 既定は変えず、先頭を見せる別の選択肢を足す | 満たす（追加の指定が要る） | 無し |
| O3 | 何もしない（`-M` を外せば行全体が見える） | 一部（長い行が画面を埋める） | 無し |

### missing

| 欠けている情報 | 状態 | 次の行動 |
|---|---|---|
| ag の実際の動作（どの選択肢で、何を単位に切り、何を付けるか） | needs-reference-check | 保守者または協力者が ag の文書とソースで確かめる |
| 既定を変えることを保守者が受け入れるか | needs-maintainer-decision | 保守者が判断する |
| 省いた部分の印の文言、長さの単位（バイトか文字か） | needs-design | 選択肢が決まった後に決める |

**【摩擦】** `needs-repro` 系の状態は使わない。要望には「参照先の確認」「保守者の方針」「設計の細部」という別の状態が要る。

### question

- 保守者へ: 既定の動作を変えてよいか、別の選択肢にすべきか。
- 起票者へ: 先頭の何文字かが見えれば目的を果たせるか。一致した箇所が先頭より後ろにあるときは、それが見えなくてもよいか。

## 最初の保守者の返答（#1）で何が変わったか

保守者は 6 時間半後に、既定は変えないと答え、その理由と代案を示した。

> The problem I have with ag's behavior is that it makes it much less obvious that a line has been truncated.

（https://github.com/BurntSushi/ripgrep/issues/1078#issuecomment-427320153 ）

同じ返答で、やるならフラグ（例 `--max-columns-preview`）にすると書いた。これで、上の O1 は却下、O2 が条件付きで残り、「切り詰めが目立たない」という**判断の基準**（制約）が出た。この基準を書く欄は試案に無い。ラベルは `enhancement` と `question` が付いた。

## 評価

### 収束を速めえた欄

- **reproduction.results の「比較対象の環境」**: 起票時点で ag の動作を `needs-reference-check` として確かめていれば、#7 で保守者が ag のソースを読むまで半年かかった確認を、最初に済ませられた。ag の選択肢は man に無く、ag の既定では切り詰めが起きないので、起票者の例を第三者が再現するのにつまずく。これはバグの再現と同じ構造で、欄はそのまま効く。
- **[[question]] と宛先**: #3 で保守者は貢献者 A に「フラグができたら使うか」と聞いた。これは需要の確認で、宛先つきの問いの欄にそのまま収まる。起票時点の問い（印の文言、単位）を先に出していれば、#7–#9 の議論は前倒しできた（推論）。
- **[[related]] の「まとめない」**: 利用者 B の要望（#5）を同じ課題に混ぜず、別のものとして並べる判断に合う。ただし関係の値に「派生した別の要望」が無い。

ただし、この課題で時間がかかった主因は理解の不足ではない。方針は #1 で 6 時間半のうちに決まり、残りの半年は実装の順番待ちと、実装してみて分かった難しさ（#9）だった（推論）。形式で縮められるのは、#7–#9 の確認と細部の決定に当たる部分に限られる。

### 合わなかった欄

- `claim.question` の「なぜ」の形: 設計どおりの動作には原因が無い。
- `expected_status` の 1 値: 「何をしてほしいかが分からない」（記述不足）と「何をしてほしいかは分かるが、すべきかで争っている」（合意の不在）を分けられない。この課題は後者で、`記述不足` を付けると、起票者に質問を返すという誤った次の行動につながる。
- `hypothesis` と `diagnosis`: 使えない。代わりに選択肢の表を自分で作った。
- `judgment.validity` の値と `judgment.severity` 全体、`judgment.upstream`。
- `same_bug_condition`、`regression_range`。

### 足りなかった欄（この課題の証拠つき）

1. **目的と使い方**: 起票者の「生成された JavaScript かを見分けたい」、貢献者 A の「長い行で画面が埋まるのを防ぎたい」（#8）、利用者 B の「一致を探してスクロールしたくない」（#5）。三者の目的は違い、O2 は前の 2 つを満たし、3 つ目は満たさない。目的が欄にあれば、#5 を範囲外とする理由が書ける。
2. **設計の選択肢と却下の理由**: O1 の却下理由（切り詰めが目立たない、#1）が残っていないと、同じ要望が再び来たときに議論をやり直す。
3. **制約・判断の基準**: 既存の利用者の互換、「既定で切り詰めない」（#6）、同じ道具の他の選択肢との一貫性（#2）、目立つこと（#1）。
4. **既定を変えるかどうか**: この課題の争点そのもの。互換と並べて独立の欄にしたい。
5. **需要の証拠**: 求める人の数と、代案で足りるか（#2–#4 で、貢献者 A は不便さから `-M` を外していた）。深刻度の代わりになる。
6. **決めるべき細部（決定点）**: 印の文言、長さの単位（バイトか書記素か）、色、複数行の一致。それぞれに「未定／決定（誰が、どこで）」を持つ。単位は議論されないまま実装で決まり、ag と食い違った。
7. **インタフェースの検証**: 名前、値を取るか、文書のどこに書くか。閉じた後に名前を直し（ef1611b）、2024 年と 2026 年にも数値を渡す誤用が報告された（#13–#15）。受け入れた後の「利用者に伝わるか」の確かめ方を書く欄があれば、スイッチではなく `-M` に値つきで指定する形を検討する材料になった（推論）。

### 欄の変更案

共通の骨格（meta、evidence、missing、question、related、judgment の priority と owner）は残し、バグ用の部分を要望用に差し替える**変種**にする。evidence や question は種類に依らず効いたので、別の形式に分けるより、`kind = "bug" | "request"` で差し替える方が保ちやすい（推論）。

```toml
[meta]
kind = "request"       # bug | request。差し替える節が決まる

[request]              # claim の代わり
situation = ""         # どんな状況で
goal = ""              # 利用者が何を果たしたいか（「なぜ」ではなく目的）
use_cases = []         # { who = "", goal = "", source = "" }。複数の目的を分けて書く
current_behavior = ""  # 観測（E の番号）
proposed_behavior = "" # 要望者の案
reference = []         # { impl = "", behavior = "", checked = false, evidence = "" }。「X のように」の X を確かめる
spec_clarity = "未確定"  # 明確 | 未確定 | 記述不足（記述不足なら要望者に質問）
agreement = "未判断"     # 合意 | 争点あり | 未判断（争点ありなら保守者の方針を問う）

[[option]]             # hypothesis の代わり。却下したものも残す
id = "O1"
statement = ""
serves = []            # 満たす use_cases
changes_default = false
compat = ""            # 既存の利用者への影響
result = "未判断"      # 採用 | 却下 | 保留
reason = ""            # 却下理由は、同じ要望が来たときに示せる形で

[[constraint]]         # 判断の基準
statement = ""         # 例: 既定で切り詰めない、切り詰めを目立たせる
source = ""            # どのコメント・方針か

[[decision_point]]     # 決めるべき細部
item = ""              # 例: 印の文言、長さの単位
state = "未定"          # 未定 | 決定
decided = ""           # 何に、誰が、どこで

[interface]            # 受け入れ後
name = ""
takes_value = false
docs = ""
misuse_check = ""      # 誤用されないかの確かめ方

[judgment.acceptance]  # validity と severity の代わり
value = "未判断"       # 受け入れ | 条件付き受け入れ | 範囲外 | 却下 | 重複 | 未判断
demand = ""            # 需要の証拠（人数、代案で足りるか）
reason = ""
decided_by = ""
```

`[[related]]` の relation に「派生した別の要望」を足し、`[[missing]]` の状態に `needs-reference-check`、`needs-maintainer-decision`、`needs-design` を足す。

## 未確認・次の一歩

- 起票時点の記録を、この課題を知らない人（または別のエージェント）に埋めさせて、同じ選択肢と決定点が出るかは試していない。
- この課題は具体的な例つきで、「何がほしいか分からない」型の記述不足ではなかった。`spec_clarity = 記述不足` に当たる要望（例の無い「Y に対応して」）にも当てて、`request` 節が足りるかを見る。
- 時間がかかった主因が実装の順番待ちだったという読みは、スレッドの日付からの推論で、保守者の記述では確かめていない。
