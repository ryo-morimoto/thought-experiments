# 課題とバグの理解の記録形式（試案）

- 状態: 試案 第 2.1 版（第 1 版を 5 件、第 2 版を 3 件に当てた）
- 作成: 2026-11-21、更新: 2026-11-21
- 根拠: [課題とバグの理解支援 先行事例](../reports/課題とバグの理解支援%20先行事例.md)、[高認知負荷の理解支援 先行事例](../reports/高認知負荷の理解支援%20先行事例.md)、[PR課題バグの安定した分類基準](../reports/PR課題バグの安定した分類基準.md)

課題（issue）やバグ報告を理解し評価するときに、何をどの欄に書くかの試案。PR と違い、課題では主張そのもの（本当に起きるか、何が正しい動作か、既知か）がまだ確定していない。そこで、この形式は「説明を読ませる」ためでなく、**主張を検証できる部品に分け、どこまで確かめたかを残す**ために作る。

## 設計の要点と根拠

<!-- data-source: original（調査の報告から筆者が作った設計の整理） -->
| 要点 | 理由（先行事例） |
|---|---|
| 観測と期待を「なぜこうなった／なぜこうならなかった」の対で書く | 期待動作を明示した報告は 35% しかない。Whyline の問いの形にすると期待が必ず書かれる |
| 期待動作の根拠と確定の状態を別に持つ | 記述不足は評価の結果として返すべき（SWE-bench Verified では 38.3% に記述不足の疑いが付いた。3 人の注釈者のうち 1 人でも重大とすれば数える保守的な集計） |
| 観測（証拠）と推論を別の欄にする | 推論と検証済みの区別は PR・課題の両方で最も基本の原理 |
| 原因の候補は「仮説＋確かめ方＋結果」で書き、棄却した仮説も残す | 位置を示しても速くならず、仮説と確かめ方を示すと成功が 6 倍（Alaboudi & LaToza）。Zeller の記録表 |
| 再現を成果物（テスト・URL・記録）にし、「同じバグ」とみなす条件を添える | 再現と診断を分ける（Pernosco、ClusterFuzz）。最小化は別のバグに化けうる（Regehr） |
| 欠けた情報を状態として持ち、次に誰が何をするかを書く | Rust の `S-needs-repro`、Kubernetes の `needs-information`。遅れの原因は誤りより欠落 |
| 未回答の問いを、報告の状態とは別に持つ | Breu: Mozilla で利用者に向けた質問の 50% が未回答 |
| 判断を欄ごとに分ける（妥当性・深刻度・優先度・担当・上流）。既定値は「未判断」。変更には理由 | Mozilla は 2020 年に深刻度と優先度を分けた。既定値が NORMAL だと評価済みか分からなかった |
| 深刻度を前提条件と緩和要因に分解する | Chromium の重大度ガイドライン、curl が CVSS をやめた理由 |
| どの時点の情報で判断したかを記録する | 起票時点の情報で判断する（BugBug）。後知恵で裁かない（Cook） |
| エージェントが出すのは仮説・確かめ方・証拠と下書きまで。判断の確定は人 | 結論として見せると人の注意が固定される（PR 側）。確信が低いときは黙る（LIBRO、BugBug） |

分類（種別、根本原因の種類）は、人が付けたラベルをそのまま信用しない（課題管理の種別ラベルの 33.8% が誤分類）。分類の欄を使うなら、定義の出典と版を書き、根拠を添えて付け直す。

## 5 件の試し打ちで変えたこと（第 1 版 → 第 2 版）

第 1 版を Firefox のバグ（下の例）と、種類の違う実際の課題 4 件に当てた。4 件は、スレッドの早い時点（as_of）でその時点の情報だけで埋め、実際の結末と比べた。記録は [examples/](examples/) にある。

| 種類 | 課題 | 分かったこと |
|---|---|---|
| 再現しない報告 | [golang/go #49679](https://github.com/golang/go/issues/49679) | 最大の手がかり（GOMAXPROCS が 5 以上で起きる）は報告者が自分から出していたが、調べ始めるまで 3 年かかり、調べてからは 1 日で説明がついた。環境を軸の表にすると、非再現側の空欄から「どの機械で試したか」を最初に聞くべきだと分かる（推論）。結末「原因不明のまま再現しなくなった」を書く欄が無かった |
| 記述不足の要望 | [ripgrep #1078](https://github.com/BurntSushi/ripgrep/issues/1078) | 要望では「なぜ」「仮説」「診断」「深刻度」が合わない。中身は明確で、既定を変えるかの合意が無いだけだった。`expected_status` 一つでは「記述不足」と誤って付け、起票者に質問を返す誤った次の行動になる。閉じた後の名前の変更と誤用（2024、2026）も、置く欄が無かった |
| AI 生成の低品質な報告 | [curl HackerOne 2298307](https://hackerone.com/reports/2298307) | 証拠の種類を数えると「観測 0、主張 3」で、仮説 3 つのうち 2 つはソースを一画面読むだけで棄却できた（保守者の最初の 2 問と同じ）。一方、主張の文、手順、実在するコードの位置、`checked_by` は LLM が簡単に偽れる。PoC が付いていても、報告者の偽サーバが自分で「TRIGGERED」と出すだけのものがあった。偽れないのは、受け手が機械で再実行・再照合できるものだけ |
| 重複の多い報告 | [kubernetes #51835](https://github.com/kubernetes/kubernetes/issues/51835) | 症状でまとめた入れ物で、中身は少なくとも 8 種類の別の原因だった。症状でなくエラー文・volume の種類・ランタイムの版で「同じバグ」を判定すると、実際の結末と一致する群に分かれた。ある群は、1 週間前に閉じた課題の修正 PR の題がエラー文そのものだった。決め手が「何をしたら消えたか」だった群もある |

ここから次のように変えた。

- **核と部品に分けた。** どの種類にも効いたのは、証拠、未回答の問い、欠けた情報、関連、判断の欄だった。原因の仮説・診断・再現はバグに、選択肢・制約・決める細部は要望に、群と報告ごとの記録は症状の入れ物に、汚染の経路はセキュリティの主張にだけ要る。全部を一つの形にすると重くなりすぎる（先行事例でも、範囲を絞ったものが成功していた）。
- **空欄が次の問いを示すようにした。** 非再現側の環境、観測の 0 件、群の判定条件など、埋まらない欄がそのまま次に聞くことになった。そこで「不明」を明示的な値にした。
- **偽れない証拠と偽れる証拠を分けた。** 報告者の主張は「主張（未確認）」として受け、受け手か機械が確かめたものだけを「観測」「文書」に上げる。コードの位置はコミット・パス・行で書き、引用はその版のソースと機械で照合する。
- **判断と結末を分けた。** 判断（妥当性・深刻度など、決めるもの）と、結末（直った、仕様どおり、再現しなくなった、分割した、など、起きたこと）は別の欄にする。
- **既定値は変えない。** 「未判断」と「迷うときはまとめない」は、4 件の実際の結末と一致した。まとめると分けるの間に「仮に入れる（未判定）」を足した。

## 第 2 版を 3 件に当て直して変えたこと（第 2.1 版の差分）

第 2 版を、種類の違う別の 3 件に当て直した（[examples/](examples/) の「第2版_」で始まる記録）。

| 種類 | 課題 | 分かったこと |
|---|---|---|
| 閉じた後に本物と分かった報告 | [golang/go #68609](https://github.com/golang/go/issues/68609) | 「使い方の誤り」として起票 13 分後に閉じ、39 分後に開き直された。`results` の受け手の行が「未実施」になり、試さずに閉じたことが見える。開き直しを動かしたのは新しい観測ではなく、別の保守者の「文書のどこにあるのか」という問いだった。決め手の欄（誰の責任か、期待の根拠）は報告者には埋めにくく、受け手がタグのソースを検索すれば数秒で埋まった |
| 本物のセキュリティ報告 | [curl HackerOne 2187833](https://hackerone.com/reports/2187833)（CVE-2023-38545）、比較に [2559516](https://hackerone.com/reports/2559516)（CVE-2024-6197） | AI 生成の報告から作った規則「受け手が再実行できる観測が要る」は、本物を誤って弾く。2187833 は再現が確率的で、2559516 はソースを読んだだけの指摘だった。引用 9 か所は配布物と機械照合して全部一致した。偽と本物を最も速く分けたのは、報告者が既存の検査を名指しして効かない理由を書いていることと、汚染の経路の第 1 段の出どころ（偽は乱数、本物は攻撃者のリダイレクト先）だった |
| 例の無い要望 | [ripgrep #169](https://github.com/BurntSushi/ripgrep/issues/169) | 空だったのは目的（問題）で、細部ではなかった。細部の欄は埋めやすいので細部の問いが先に出やすいが、却下されれば無駄になる。本当の需要が出たのは「出力を何に流すのか。この代案で足りないか」という、用途と試せる代案を組にした 2 問目だった |

変えたこと:

- **セキュリティの規則を緩めた。** 妥当性の条件を「受け手の観測」から「観測、または機械照合を通った経路と値の条件」に変える。数値が合わないときは棄却せず問いを返す。時間だけを変える書き換え（遅延の挿入など）で得た再現は観測として数える。位置はタグも受け付け、指定の版で照合する。到達すれば必ず誤りの欠陥では、経路の細部を妥当性でなく深刻度の判断に回す。
- **閉じる前の検査を足した。** 「無効」「使い方の誤り」で閉じる前に、(1) 受け手が試した結果の行、(2) 誤用とするなら破った契約の出典、(3) 部品の語での重複検索、の 3 つをそろえる。起票直後のトリアージで全欄を埋めるのは重すぎるので、閉じるときだけこの 3 つを求める。
- **判断に根拠と履歴を持たせた。** 開き直しは新しい観測なしに起きた。判断がどの証拠に依ったかと、変わった履歴を残す。
- **要望の目的を問題と解決案に分けた。** 問題が空なら XY 問題（本当の問題とは別の解決策を頼んでいる状態）を疑い、目的を先に聞く。細部は受け入れが決まってから決める。

```toml

[[dup_search]]
query_kind = ""            # エラー文 | 部品の語。エラー文で見つからない前例が、部品の語で見つかった例がある

[[hypothesis]]
location = ""              # 疑う場所（版つき）。場所が動いた履歴を残す

[[related]]
differs_in = ""            # 前例と違う点（例: 前例は第三者のサーバだった）

[judgment.validity]

history = []               # { at, value, by, reason } の並び
close_gates = {}           # 無効・誤用で閉じる前に: receiver_result（受け手の結果の行）、contract_source（破った契約の出典）、component_dup_search
```

担い手についての観察:

- **決め手の欄は受け手側が埋める。** 誰の責任か、期待の根拠、引用の照合は、報告者に聞き返しても埋まらず、受け手（エージェントや機械）がソースを読めば数秒〜数分で埋まった。
- **本物のセキュリティ報告では、報告者が欄のほぼ全部を埋めていた**（条件、経路の段、修正案）。受け手の仕事は照合と、深刻度の前提・緩和要因の判断だった。
- **要望の目的は起票者しか埋められない**が、どう聞くかはエージェントが下書きできる（XY 問題の検知、用途と代案を組にした問い）。範囲の方針と、ライブラリの切り出しのような保守者しか知らない選択肢は保守者が埋める。

## 誰が埋めるか、どこまで埋めれば渡せるか

欄が増えたので、全部を誰かが埋める前提にすると重さで使われなくなる。そこで、担い手ごとに受け持つ欄を決め、段階ごとに「最低限ここまで埋まれば次へ渡せる」を決める。

### 担い手

| 担い手 | 受け持つ欄 | 理由 |
|---|---|---|
| 報告者 | `claim.observed`、手元の環境の 1 行、`question` への返答、報告者に向けた `hypothesis` の確かめ（`who_can_test = 報告者`）、`reporter_labels` | 報告者は手元で数分で確かめられることを持っている（golang/go #49679 の GOMAXPROCS は報告者が自分から出した）。一方で、開発者に要る情報の多くは報告者には集めにくい（Zimmermann 2010） |
| 調べる人（エージェント、またはトリアージの担当） | `evidence` の収集、`dup_search`、`related` の下書き、`env_axes`、`hypothesis` と `how_to_test` の下書き、`missing` と `next`、`question` の下書き、判断の下書き（`decided_by = 下書き`） | 集めにくい情報の収集を代行するのが調べる人の役目。仮説は答えでなく確かめ方つきで渡すと人を助ける（Alaboudi & LaToza） |
| 機械（スクリプト、CI） | `evidence.mechanical_check`（引用したコードをその版のソースと照合、試験の再実行、エラー文での検索）、`taint_path` の各段の行の存在、`value_condition` と本文の数値の矛盾の検出 | 偽れないのは受け手が機械で再実行・照合できるものだけだった（curl HackerOne 2298307） |
| 保守者（判断する人） | `judgment.*` の確定、`expected_status` と `agreement` の確定、`related.merge` の確定（とくに「まとめる」）、`resolution`、`deferral` | 判断と予定は受け手の責任（Mozilla の Severity と Priority）。誤ってまとめる害が大きい（Sentry） |

`evidence.checked_by` は報告者が書かない。報告者が書いた事実はすべて「主張（未確認）」で受け、調べる人か機械が確かめて「観測」「文書」に上げる。

### 段階ごとの最低限

各段階で、表の欄が埋まっていれば次へ渡す。埋まらない欄は空にせず、`不明` と書くか、`missing` に状態と `next` を書く。**空欄のまま渡さない**ことだけを最低限の規則にし、全部を確かめてから渡すことは求めない。

| 段階 | 渡す先 | 最低限（バグ） | 最低限（要望） | 最低限（症状の入れ物） |
|---|---|---|---|---|
| 1. 受け付け | 課題管理 | `meta.source`、`claim.observed`、環境 1 行（不明可）、`evidence` 1 件以上（主張（未確認）でよい） | `request.purpose`、`use_cases` 1 件以上 | 各報告の `fingerprint`（最初のエラー文。無ければ不明） |
| 2. 調査へ | 調べる人 | `claim.expected` と `expected_basis`（決められなければ `expected_status = 記述不足` と、`asks_for` つきの `question`）、`dup_search` 1 件以上（エラー文で）、`reproduction.artifact` か `missing: needs-repro` | `spec_clarity` と `agreement`、`references` の確認の有無、記述不足なら `asks_for` つきの `question` | `cluster` ごとの `same_bug_condition`、報告の `cluster` の割り当て（仮に入れる、でよい） |
| 3. 判断へ | 保守者 | 主要な主張が観測・文書（`mechanical_check` つき）、`hypothesis` 1 件以上に `how_to_test` と結果、`env_axes` と再現しない側の行、判断の下書き（理由と確信度つき） | `option` 2 件以上（「何もしない」を含む）、`constraint`、`decision_point` | 群ごとの `resolving_action` か `missing`、`tracked_in` |
| 4. 上流へ | 他のプロジェクト | `judgment.upstream.gates` がすべて通る（とくに「公開してよい内容か」）、`dup_search` の記録、`taint_path`（セキュリティのとき） | （上流への要望は同じ門を通す） | （群ごとに 4 を当てる） |

渡すときに、段階 1〜3 のどこまで埋まっているかを `meta` に書く（`meta.stage`）と、受け手が何をすればよいかが分かる（推論。試していない）。

## この例で分かったこと

- **深刻度の欄を前提条件と緩和要因に分けたことで、報告の経路が変わった。** 先に作った上流への報告の下書きは、公開のバグ（1760782）へのコメントか新しい公開のバグを考えていた。深刻度を分解すると、本件は credentialless という漏洩対策の迂回で、攻撃者が前提を自分で整えられる。そうであれば、Mozilla のセキュリティバグの手続き（非公開の報告）で出し、深刻度の判断は受け手に任せるのが筋になる（推論）。「公開してよい内容か」の門は、この例を書いて足した。
- **棄却した仮説を残す欄が、受け手の手間を減らす。** H1〜H3 は受け手が最初に疑う点で、それぞれの棄却の根拠（E3、E4、E5）を添えると、報告の妥当性を確かめる時間が減る（curl の「棄却のコスト」の逆）。
- **試験の問題（H6）と本件を分ける欄が要った。** 実際の調査では、試験が Firefox で止まる問題と本件が絡み合っていた。related に「試験の問題」の関係を置いたことで、まとめずに並べられた。
- **重かった欄**: evidence と hypothesis。この例では、エージェントが仕様・試験・ソースを調べて埋めた。人が手で埋めるのは重いので、仕組みにするなら、エージェントが下書きし、人は判断の欄を確定する分担になる。
- **足りなかった欄**: 影響の確かめ方（missing の 3 行目）。深刻度の判断に要る試験を、仮説と同じ「確かめ方」の形で書ける欄があるとよい。

## 未確認・次の一歩

- 第 2 版は、5 件の試し打ちで出た提案を入れただけで、第 2 版そのものはまだどの課題にも当てていない。各種類で別の 1 件に当て直す必要がある。特に「cannot reproduce で閉じて、後から本物と分かった」型（golang/go #49679 は閉じずに放置した型だった）、例の無い本物の記述不足の要望、本物のセキュリティ報告（taint_path と機械照合の規則が正しい報告を誤って弾かないか）。
- 試し打ちの評価（「この欄があれば早く着けた」）は、結末を知った後の推論で、後知恵が混じる。群の分け方（重複の多い報告）も一人の判断で、別の人が分けて一致するかは確かめていない。
- 欄が増えた。誰がどの欄を埋めるか（報告者・エージェント・保守者）と、最低限どこまで埋めれば受け手に渡せるかを決めないと、重さで使われなくなる。
- この形式で書くと、受け手の理解（再現の成否、診断の一致、判断の時間）が良くなるかは測っていない。先行事例でも、課題の理解支援の効果を測った対照実験はほとんど無い。
- 上流への報告の推奨（非公開のセキュリティ報告）は推論で、まだ送っていない。送るかどうかはユーザーが決める。
