# 課題とバグの理解の記録形式（試案）

- 状態: 試案（1 件に当てただけ）
- 作成: 2026-11-21
- 根拠: [課題とバグの理解支援 先行事例](../reports/課題とバグの理解支援%20先行事例.md)、[高認知負荷の理解支援 先行事例](../reports/高認知負荷の理解支援%20先行事例.md)、[PR課題バグの安定した分類基準](../reports/PR課題バグの安定した分類基準.md)

課題（issue）やバグ報告を理解し評価するときに、何をどの欄に書くかの試案。PR と違い、課題では主張そのもの（本当に起きるか、何が正しい動作か、既知か）がまだ確定していない。そこで、この形式は「説明を読ませる」ためでなく、**主張を検証できる部品に分け、どこまで確かめたかを残す**ために作る。

## 設計の要点と根拠

<!-- data-source: original（調査の報告から筆者が作った設計の整理） -->
| 要点 | 理由（先行事例） |
|---|---|
| 観測と期待を「なぜこうなった／なぜこうならなかった」の対で書く | 期待動作を明示した報告は 35% しかない。Whyline の問いの形にすると期待が必ず書かれる |
| 期待動作の根拠と確定の状態を別に持つ | 記述不足は評価の結果として返すべき（SWE-bench Verified では 38.3% に記述不足の疑いが付いた。3 人の注釈者のうち 1 人でも重大とすれば数える保守的な集計） |
| 観測（証拠）と推論を別の欄にする | 推論と検証済みの区別は PR・課題の両方で最も基本の原理 |
| 原因の候補は「仮説＋確かめ方＋結果」で書き、棄却した仮説も残す | 位置を示しても速くならず、仮説と確かめ方を示すと成功が 6 倍（Alaboudi & LaToza）。Zeller の記録表 |
| 再現を成果物（テスト・URL・記録）にし、「同じバグ」とみなす条件を添える | 再現と診断を分ける（Pernosco、ClusterFuzz）。最小化は別のバグに化けうる（Regehr） |
| 欠けた情報を状態として持ち、次に誰が何をするかを書く | Rust の `S-needs-repro`、Kubernetes の `needs-information`。遅れの原因は誤りより欠落 |
| 未回答の問いを、報告の状態とは別に持つ | Breu: Mozilla で利用者に向けた質問の 50% が未回答 |
| 判断を欄ごとに分ける（妥当性・深刻度・優先度・担当・上流）。既定値は「未判断」。変更には理由 | Mozilla は 2020 年に深刻度と優先度を分けた。既定値が NORMAL だと評価済みか分からなかった |
| 深刻度を前提条件と緩和要因に分解する | Chromium の重大度ガイドライン、curl が CVSS をやめた理由 |
| どの時点の情報で判断したかを記録する | 起票時点の情報で判断する（BugBug）。後知恵で裁かない（Cook） |
| エージェントが出すのは仮説・確かめ方・証拠と下書きまで。判断の確定は人 | 結論として見せると人の注意が固定される（PR 側）。確信が低いときは黙る（LIBRO、BugBug） |

分類（種別、根本原因の種類）は、人が付けたラベルをそのまま信用しない（課題管理の種別ラベルの 33.8% が誤分類）。分類の欄を使うなら、定義の出典と版を書き、根拠を添えて付け直す。

## 欄の定義

```toml
[meta]
source = []            # 元の課題・報告・スレッドの URL
as_of = ""             # どの時点の情報で書いたか（日時、スレッドのコメント番号、対象の版）
versions = {}          # 対象のソフトウェア・仕様・試験の版やコミット

[claim]                # 主張。why did / why didn't の形
question = ""          # 例: 「なぜ X は Y を返したのか」「なぜ Z は起きなかったのか」
observed = ""          # 観測した動作（OB）
expected = ""          # 期待した動作（EB）
expected_basis = []    # 期待の根拠: 仕様の箇所、以前の動作、他の実装、報告者の思い込み、のどれか
expected_status = "未確定"   # 確定 | 未確定 | 記述不足（記述不足なら、推測せず質問する）

[reproduction]
artifact = ""          # 再現の成果物（試験ファイル、URL、記録）
steps = []             # 再現手順（S2R）
same_bug_condition = ""  # 最小化や移植で「同じバグ」とみなす条件
results = []           # { env = "", result = "", evidence = "" } の並び。比較対象の環境も入れる
regression_range = "未実施"  # 最後に動いた版と最初に壊れた版。未実施 | 該当なし（理由）| 範囲

[[evidence]]           # 観測した事実。推論はここに書かない
id = "E1"
kind = "観測"          # 観測 | 文書（仕様・ソースの記述）
statement = ""
source = ""            # 試験の出力、ログ、仕様の URL、ソースの位置（版つき）
checked_by = ""        # 誰・何が確かめたか

[[hypothesis]]         # 原因の仮説。棄却したものも残す
id = "H1"
statement = ""
how_to_test = ""
result = "未検証"      # 支持 | 棄却 | 未検証
evidence = []          # E の番号

[diagnosis]
chain = []             # 因果の連鎖（入力から症状まで）。各段に E の番号を付ける
confidence = ""        # 高 | 中 | 低。理由も書く
unverified = []        # 診断のうち確かめていない部分

[[missing]]            # 欠けた情報。状態として持つ
item = ""
state = ""             # 例: needs-repro, needs-bisection, needs-spec-check, needs-runtime-check
next = ""              # 次に誰が何をするか

[[question]]           # 未回答の問い（議論の状態）
text = ""
to = ""                # 誰に向けた問いか
answered = false

[[related]]
link = ""
relation = ""         # 同じ原因 | 同じ症状 | 前提 | 試験の問題 | 実装の経緯
evidence = ""
merge = "まとめない"   # まとめる | まとめない（迷うときはまとめない）

[judgment.validity]    # 判断。既定は「未判断」。確定は人、エージェントは下書きまで
value = "未判断"       # 妥当 | 無効 | 重複 | 情報不足 | 未判断
reason = ""
confidence = ""
decided_by = ""        # 人の名前、または「下書き（エージェント）」
at = ""

[judgment.severity]    # 影響。予定（優先度）と混ぜない
value = "未判断"
preconditions = []     # 成立に必要な前提
mitigations = []       # 緩和要因
most_general_condition = ""  # 再現する最も一般的な条件
reason = ""
decided_by = ""

[judgment.priority]    # いつやるか。多くは受け手の側が決める
value = "未判断"
decided_by = ""

[judgment.owner]
component = ""
root_cause_likely_in = ""
ownership_unclear = false

[judgment.upstream]    # 上流へ報告するか、どの経路で
gates = {}             # 最小再現 / 回帰範囲 / 環境に固有でない / 重複の確認 / 検証できる主張だけ / 公開してよい内容か
route = ""             # 公開の課題 | 既存の課題へのコメント | 非公開のセキュリティ報告 | 報告しない
value = "未判断"
decided_by = ""
```

## 例: Firefox の credentialless と service worker のバグ

思考実験「ブラウザの意味論から検証モデルへの変換に健全性の根拠を与えられるか」の過程で見つけたバグに当てた。事実はその過程で確かめたもので、出典はこの会話の調査（WPT の実行、仕様の照合、Gecko のソースの読解）にある。

### meta

- source: 自前の WPT の実行（WPT 31362d1）。関連する既存の課題は下の related。
- as_of: 2026-11-21。Gecko は firefox-main の 437dd72 を読んだ（160.0.1 のリリース版のソースではない）。
- versions: Firefox 160.0.1、Chrome 158.0.8127.36、WPT 31362d12238db2b16efda9643953d6e4630caf7b、Fetch 標準（2026-11-21 時点）。

### claim

- question: **なぜ**、COEP credentialless の文書は、service worker が資格情報つきで取った CORP 無しの他サイトの応答を、**拒否しなかったのか**。
- observed: COEP unsafe-none の service worker が `credentials: "include"` で取った no-cors の応答を `respondWith()` で渡すと、文書の `fetch(url, {mode: "no-cors"})` が opaque で解決する。
- expected: ネットワークエラー。
- expected_basis:
  - Fetch の HTTP fetch: CORP の検査は service worker から来た応答にも、クライアントの埋め込みポリシーで行う。
  - Fetch の CORP の内部検査: `credentialless` のとき、応答の request-includes-credentials が真なら policy を `same-origin` にする。
  - 応答の request-includes-credentials の既定値は真。service worker 自身の取得でも真になる。
  - 他の実装: Chrome 158 はエラーにする。
- expected_status: 確定（仕様の文は一意で、仕様への未解決の課題も見つからなかった）。

### reproduction

- artifact: `wpt-draft/service-worker-coep-none-proxy-credentials.https.window.js`（思考実験のブランチ）。service worker の中の `serviceWorker.state` を `registration.active.state` に直した版。
- same_bug_condition: 「credentialless の文書」「service worker が渡した応答」「資格情報つきで取った」「CORP 無し」「他オリジンの no-cors」がそろい、文書の取得がエラーにならないこと。どれか 1 つでも欠けた場合は同じバグとみなさない。
- results:

| 環境 | 資格情報つき（本件） | 資格情報なし | 対照（COEP なしの文書） | 文書から直接 `include` |
|---|---|---|---|---|
| Chrome 158 | エラー（期待どおり） | opaque | opaque | opaque |
| Firefox 160.0.1 | **opaque** | opaque | opaque | opaque |

- regression_range: 該当なし。Firefox が credentialless を出した 119 から、この経路は直っていなかった可能性が高い（未確認）。

### diagnosis

- chain: (1) service worker が資格情報つきで取得し、応答は資格情報つきになる → (2) `StartSynthesizedResponse` が応答の資格情報モードを写さずに文書のチャネルへ渡す（E8） → (3) 文書のチャネルで CORP の検査が走る（E5） → (4) credentialless の分岐が `CorsIncludeCredentials` を読み、no-cors なので常に偽（E6、E7） → (5) policy が空のまま許可され、opaque が文書に届く（E1）。
- confidence: 中〜高。ソースの読解と実行結果が一致する。
- unverified: 160.0.1 のリリース版のソースとの同一性、実行時の確認（デバッガやログ）、試験を有効にしたとき 1613912 による別の失敗が出るか。

## この例で分かったこと

- **深刻度の欄を前提条件と緩和要因に分けたことで、報告の経路が変わった。** 先に作った上流への報告の下書きは、公開のバグ（1760782）へのコメントか新しい公開のバグを考えていた。深刻度を分解すると、本件は credentialless という漏洩対策の迂回で、攻撃者が前提を自分で整えられる。そうであれば、Mozilla のセキュリティバグの手続き（非公開の報告）で出し、深刻度の判断は受け手に任せるのが筋になる（推論）。「公開してよい内容か」の門は、この例を書いて足した。
- **棄却した仮説を残す欄が、受け手の手間を減らす。** H1〜H3 は受け手が最初に疑う点で、それぞれの棄却の根拠（E3、E4、E5）を添えると、報告の妥当性を確かめる時間が減る（curl の「棄却のコスト」の逆）。
- **試験の問題（H6）と本件を分ける欄が要った。** 実際の調査では、試験が Firefox で止まる問題と本件が絡み合っていた。related に「試験の問題」の関係を置いたことで、まとめずに並べられた。
- **重かった欄**: evidence と hypothesis。この例では、エージェントが仕様・試験・ソースを調べて埋めた。人が手で埋めるのは重いので、仕組みにするなら、エージェントが下書きし、人は判断の欄を確定する分担になる。
- **足りなかった欄**: 影響の確かめ方（missing の 3 行目）。深刻度の判断に要る試験を、仮説と同じ「確かめ方」の形で書ける欄があるとよい。

## 未確認・次の一歩

- この形式は 1 件にしか当てていない。種類の違う課題（再現しない報告、記述不足の機能要望、重複の多い報告、低品質な AI 生成の報告）に当てて、欄の過不足を見る。
- この形式で書くと、受け手の理解（再現の成否、診断の一致、判断の時間）が良くなるかは測っていない。先行事例でも、課題の理解支援の効果を測った対照実験はほとんど無い。
- 上流への報告の推奨（非公開のセキュリティ報告）は推論で、まだ送っていない。送るかどうかはユーザーが決める。
