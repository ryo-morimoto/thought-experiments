## 段階B（評価）

### 実際の経過（要約）

- 2021-03-23 共同管理者の最初の返答は、テキストの定義を問うものだった（ASCII か、UTF-8 か、MIME か）。「How do you define a text file?」 https://github.com/sharkdp/fd/issues/749#issuecomment-805155085
- 要望者は定義（NUL を探すヒューリスティック）だけ答え、目的は書かなかった。第三者が fzf に渡す用途と `file` を使った回避策を書いた。
- 2021-08-08 所有者は `--type` に text/binary を足す案に「入れる方に傾いている」と書き、good first issue を付けた。貢献者が実装の段取り（先頭 n バイト、`--type file` との組み合わせ、テスト）を質問し、所有者と共同管理者が「先頭 1024 バイト程度」と答えた。
- 2021-08-09 所有者が方向を戻し、用途を尋ねた。「could you tell us a bit more about your use case?」 https://github.com/sharkdp/fd/issues/749#issuecomment-895523174 同日、共同管理者が回避策 `fd -t f -X grep -lI .`（空ファイルは出ない）を示した。
- fzf の利用者は「いまはほとんど要らない」と答えた。要望者からの回答はなかった。
- 2021-11-14 所有者が閉じた。「Ok, we haven't seen any real use case except for the minor "inconvenience". Closing this for now.」 https://github.com/sharkdp/fd/issues/749#issuecomment-968322639
- 閉じた後（2023〜2024）に、tar でのバックアップ、neovim の telescope など別の用途が 3 件書かれたが、再開はされていない。2022-12 に #1208「binary and text file types」が相互参照された。
- GitHub 上の stateReason は COMPLETED だが、実装はされていない。実質は「需要が示されないので保留して閉じる」。

正直に言うと、到達した段階は「1 未満、または 3」のどちらとも言える。本件の要望者自身の use case は 0 件で、stages.md 45 行の「≥1 use case」は #532 から借りた use case を数えたときにしか満たせない。借用を数えれば、段階2（spec_clarity、agreement、references の確認）と段階3（何もしない・回避策を含む 5 つの選択肢、出典つきの constraint）の最低限は満たしている。スキルは借用を数えてよいか、段階が累積かを書いていないので、`stage = 3` に注記を付けるしかなかった。

### 一人で埋められた項目と、相手が要った項目

- 一人で埋められた: evidence（E2〜E6）、references の確認、dup_search、related、option（O1〜O5）、constraint、decision_point、questions の下書き。

### 段階A の誤りと、スキルが捕まえたか

### 使いにくさ

- 要望には「エラー文」がない。workflow.md 4 行と core.md 56 行は重複検索を「エラー文」と「部品の用語」で 2 回行うよう求め、stages.md 46 行の Bug 列もエラー文での検索を求める。要望では「提案された解決の用語」と「問題の用語」の 2 回に読み替えた。
- output.md 60 行（主張を「なぜ〜したか／しなかったか」の形で書く）と 62 行（仮説の上位 2 つと検証方法）は要望に合わない。要望では「選択肢の上位 2 つと、何を確かめれば選べるか」に読み替えた。
- workflow.md 6 行の「原因を仮説として書く」も要望には当てはまらない。要望の場合に飛ばしてよいと書かれていない。
- judgments.md の validity、owner.root_cause_likely_in、upstream は要望ではほぼ「該当なし」になる。output.md 69 行は「種類に応じた部分だけ」と言うが、judgments.md のどれが要望に要るかは書いていない。結局全部書いて「該当なし」で埋めた（workflow.md 7 行の「空欄にしない」との兼ね合い）。
- judgments.md 3 行は各判断に reason・confidence・based_on を求めるが、request.md 105-108 行の `[judgment.acceptance]` には confidence と based_on がない。コメントで補った。
- acceptance の値（request.md 106 行: 受け入れ／却下／回避策で足りる／未判断）に「需要が示されるまで保留」がない。実際の結論はこれだった。`deferral`（core.md 61-64 行）は近いが、判断の値と結びついていない。
- 「借用した use case」を数えてよいか、段階が累積か（stages.md 41-47 行）が書かれていない。
- 過去に同じ要望が閉じられている場合、その時の所有者の発言を `constraint` に置くのか `agreement` の根拠に置くのか書かれていない。constraint に置いたのは有効だった。
- as_of 後に見えてしまった情報、トラッカーの状態値（stateReason）を信用しないこと、を書く場所がない。reporter_labels（core.md 22 行）と同じ扱いが要る。

### スキルへの提案

1. 要望用の読み替えを明記する。workflow.md 4 行に「要望ではエラー文の代わりに、提案された解決の用語と、問題の用語で検索する」を足し、core.md 56 行の query_kind に `solution terms | problem terms` を足す。workflow.md 6 行と output.md 60・62 行に「要望では仮説の代わりに選択肢と、選ぶために確かめること」を足す。
2. request.md 105-108 行の `[judgment.acceptance]` に `confidence` と `based_on` を足し、value に `保留（需要待ち）` を足す。閉じた後の use_cases（76 行の at）が増えたら見直す、と結びつける。
3. request.md 82-89 行の option に「回避策は対象ツール自身の機能（例: fd の `-X`）と組み合わせた形も探して試す」を足す。あわせて stages.md 45 行に「use case は別の報告から借りてよい。出典と at を書き、本件の要望者のものと分ける」「段階は累積」を書き、request.md 91 行に「同じ要望が過去に閉じられていれば、その時の所有者の発言を constraint に出典つきで置く」を足す。

ほかに、workflow.md 1 行（3 行目）に「as_of 後に目に入った情報を `meta` に書き、トラッカーの状態値は reporter_labels と同様に信用しない」を足すとよい。core.md 47-49 行の relation には `generalization`（同じ要望を含む汎用案）が欲しい。
