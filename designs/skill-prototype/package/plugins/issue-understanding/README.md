# issue-understanding

> **検証中（experimental）です。** より良いスコープに組み替える可能性が高く、名前・構成・記録の書式は、予告なく変わります。

## 目的

課題（issue）やバグ報告を、理解し評価するための記録を下書きします。PR と違い、課題では主張そのもの（本当に起きるか、何が正しい動作か、既知か）がまだ確定していません。そこで、説明を書くのではなく、**主張を検証できる部品に分け、どこまで確かめたかを残す**ことを目的にします。

人が判断する部分は自動化しません。エージェントは、証拠の収集、機械での照合、重複の検索、仮説と確かめ方の下書き、欠けた情報と問いの整理、判断の下書きまでを担います。**判断の確定と、報告者や上流への連絡は、人が行います。**

## 構成

| 部品 | 種類 | 内容 |
| --- | --- | --- |
| `evaluating-issue-reports` | skill | 記録の下書きの手順と、種類（バグ・要望・症状の入れ物・セキュリティの主張）ごとの欄 |
| `scripts/check_limits.py` | script | skill のファイルの文字数と、参照の案内漏れを検査する |
| `evals/` | 評価ケース | 試用で見つかった失敗（多義的な語、目的の無い要望、生成された脆弱性報告、誤用としての早すぎる close）を、合格の条件つきで書いたもの |

## 設計の根拠

記録の形式は、先行事例の調査と、実際の課題 10 件ほどへの試し打ちから作りました。調査と試し打ちの記録は、別のリポジトリにあります（[ryo-morimoto/thought-experiments の designs/](https://github.com/ryo-morimoto/thought-experiments/tree/worktree-comprehension-prior-art/designs)）。主な根拠は次のとおりです。

- 開発者に要る情報と報告者が出す情報はずれており、遅れの原因は誤った情報より欠けた情報（Zimmermann ら、TSE 2010）。
- 原因の場所を順位で示しても人は速くならず（Parnin & Orso、ISSTA 2011）、仮説を確かめ方つきで示すと修正の成功が増えた（Alaboudi & LaToza、VL/HCC 2020）。
- 偽りにくいのは、受け手が機械で再実行・照合できる証拠だけだった（curl への生成された脆弱性報告での試し打ち）。

## 正直な限界

- 試用は各種類 1〜2 件で、評価も小規模です。この記録で書くと受け手の理解や判断が良くなるかは、測っていません。
- 評価ケースは、試用から作ったもので、まだスキルあり・なしで実行していません。
- セキュリティの規則は、偽の報告 2 件と本物の報告 2 件でしか確かめていません。
